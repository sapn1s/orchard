## Violated invariant
The orchestrator's live context should hold only what must survive across dispatches — decisions, the plan, standing instructions, what each lane was told, the compaction summary. A lane's **full result prose is durable reference material, not active orchestration state**: it is read once and then re-read (as cache) on every subsequent turn for the life of the session, whether the parent ever needs its detail again or not.

## The design that produces this class
An in-process `Agent`-tool lane returns its **entire final message as the tool_result**, which the claude CLI/SDK folds into the parent's context stream. Compaction bounds the parent's *size* (FEAT-123: ~400–540k tokens/turn, flat across 3,521 turns) but not its *composition*: the accumulated lane prose is replayed every turn as cache-read. Measured: cache-read is **$2,834 (54%)** of the session's $5,142; lane-result prose is **~28%** of what the parent carries — the largest single reducible category. The parent pays continuously for recall it uses rarely.

## Why local patches did not hold
- **Compaction (FEAT-113)** bounds total size but keeps replaying prose — attacks size, not composition.
- **Session reset** re-pays cold cache writes and the steady state is already bounded (FEAT-123) — buys little.
- **WA v4 §I already says "your context is a liability, relay findings"** — but it never specifies the *lane-final-message contract*, so lanes return full reports and the parent ingests them. Prose-only guidance, same failure as FEAT-096/108/100. The fix must be structural: put the contract where it is injected into every lane's prompt.

## The fork it decides, and the evidence that decided it
The one genuine fork is **how much instant recall the parent trades for cost**:
- **A — Full recall (status quo):** every lane's full prose stays in parent context. Most expensive.
- **B — Pointer-only:** lane's final message to the parent = compact verdict + decisions + a durable pointer; full detail goes to the ticket Activity log / report file; parent re-fetches on demand (`scripts/harvest-agent.mjs`, FEAT-111, reads a child's report by id without ingesting its transcript).
- **C — Rebuild-from-board:** parent carries almost nothing, reconstructs state from the board when needed. Cheapest, riskiest (latency + stale/absent recall).

**Decided from the user's real message history**, not from preference (the user explicitly delegated this to the data). Method: extracted every human-typed turn from the 32-day mega-session transcript (`87564f3e-…jsonl`, 22,989 records), filtering out tool-results, task-notifications, system-reminders and injected briefings → **546 real human messages**. Classified for the decisive pattern: *does the message require the parent to recall a prior lane's DETAILED findings from live context?*
- **Recall-of-lane-detail follow-ups: ~0** (0–2 at the loosest reading, and both of those are design discussions, not "tell me what lane X found"). ~143 are control/short ("ok", "continue", "u can restart", "approved"); ~401 are new dispatches, UI/UX feedback, or design/process discussion.
- Of the 9 messages that reference a ticket ID with a question and the 13 with a prior-referencing noun ("that fix", "the finding"), **none** ask the parent to replay lane prose — they are feedback on the **board/UI** ("this Needs-you card lacks the question", "I don't see the change to ARCH-005", "have you already addressed it? I'll go to the board and see").
- The user repeatedly states their own recall pathway IS the board: *"either i tell u and u can act — you get at least sometimes-refreshed context of ticket states yourself"*; *"i will then go to board and see."*

**Conclusion: B is decisively correct.** Follow-ups needing parent-held lane detail are essentially absent; the user already treats the board as the source of truth, which also directionally validates C as the eventual lean end (do not build C now — see What NOT to do).

### Cross-provider decorrelation (OpenAI gpt-5.6-sol, one pass, 16.3k tokens / ~$0.02 est)
Independently chose **B** on the same reasoning (compaction attacks size not composition; B targets the dominant avoidable spend; the retrieval path already exists; C removes too much operational state). It **disputed one thing in our framing, correctly**: low *user* follow-up frequency does not by itself make B safe, because **internal orchestration decisions** can need a prior lane's detail even when the user never asks. Its decision variable is not raw frequency but `retrieval_frequency × latency/cost + P(fail-to-retrieve) × consequence`, and it insists B ship with **mandatory machine-detectable retrieval triggers** ("harvest before you revisit, challenge, merge, or implement a detail-dependent finding") and **durable provenance** (report id + timestamp), "not as a simple replacement of prose with a filename." This is folded into the spec below (B1.3, B1.4). It added nothing that changes the A/B/C choice; it hardened the contract.

## Decision — which point on the recall/cost fork, and is it a build
- **A — Full recall (status quo).** Keep every lane's full prose in parent context. Rejected: it is the measured cost driver ($2,834 cache-read, 28% lane prose) buying recall the history shows is essentially never exercised.
- **B — Pointer-only + on-demand harvest (CHOSEN).** Lane final message = compact verdict + decisions + durable pointer; full detail to the Activity log; parent harvests on demand, with mandatory retrieval triggers. Attacks the dominant spend, keeps the safety of on-demand detail, uses infra that already exists.
- **C — Rebuild-from-board only.** Deferred, not rejected: directionally validated by the user's board-first behaviour, but too much operational state removed to adopt now (stale/absent-recall risk). Revisit after B has run and the harvest-frequency data is in.

## Implementation spec (ordered; build lanes execute without further design)

**B1 — the lane-final-message contract (primary lever, no service code, provider-agnostic).**
1. **RESPONSE_FORMAT.md injected core** (`templates.ts#responseFormatSection`, injected into every lane's system prompt, gated on `responseDigest.enabled`): add one rule to the injected region — *a lane's FINAL message to its orchestrator is a compact handoff: the verdict/outcome, the decisions made, and a pointer (ticket id + Activity-log entry, and the `<output-file>`/report id) to the full detail. The full detail goes to the ticket Activity log, NOT into the final message.* This is the enforcement surface because it reaches every lane and is paid once per turn (keep it to a definition + a rule per the file's size budget; reasoning lives outside the inject markers). The existing `orchard-outcome` / `orchard-finding` prose blocks are the natural carriers.
2. **WA v4 §I** (`docs/prompts/WORKING_AGREEMENT.v4.md`, edit canonical in `~/projects/methodology` then `sync:methodology` — never the mirror): under "keep your own context lean", add the reciprocal rule for what a lane RETURNS (today §I only tells the orchestrator to keep ITS context lean; it never constrains the lane's return payload). One paragraph: the lane's final message is a compact verdict + decisions + pointer; detail belongs in the Activity log; the orchestrator relays the compact form and does not paste lane prose into its own context.
3. **Retrieval triggers (OpenAI hardening) in WA §I:** the orchestrator MUST harvest the full report (`scripts/harvest-agent.mjs <agent-id>`) before it *revisits, challenges, merges, or implements* a detail-dependent finding — not only when the user asks. State it as a machine-checkable trigger list so a later audit can catch a silent non-retrieval.
4. **Durable provenance in the pointer:** the pointer must carry a stable report id + timestamp (harvest-agent already locates by agent id; the Activity-log entry is the durable anchor), so a re-fetch cannot resolve to a moved/stale artifact.
5. **Charter template:** whichever charter the orchestrator writes must instruct the lane to end with the compact contract (a one-line addition to the standing dispatch preamble); `docs/prompts/patterns/*` and the dispatch charter guidance reference the same rule.

**B2 — trimming the injected notification body: SCOPE CORRECTION (build lanes: do NOT attempt the original framing).**
The ARCH context finding proposed "Orchard trims the injected notification body to pointer+summary." Verified against the code, this is **not reachable at Orchard's layer for the dominant path**: the in-process `Agent`-tool result returns to the parent as the CLI/SDK's **tool_result**, and Orchard does not sit in that stream. Orchard's only hooks are `PreToolUse` allow/deny (`claude-runtime.ts` ~551; `orchestrator-profile.mjs#decide` — it can DENY, it cannot REWRITE), and its sole prompt-injection surface is `#withBriefing` prepending to the *user's* turn prompt (`agent-bridge.ts` ~1472). Rewriting the tool_result would mean touching the claude-station service / CLI internals — **out of scope and forbidden**. The paths Orchard DOES compose — the `#withBriefing` "while you were away" text and background-task `task_notification` frames — are **already pointer+summary** (this session's own notifications carry `<summary>` + `<output-file>`, not full prose). So B2 as a trim buys ~nothing; the saving lives entirely in B1 (make the final message compact at the source, so the tool_result the CLI returns is already small). **Build item for B2:** none beyond (a) an anti-regression test asserting the briefing/notification paths stay pointer-shaped, and (b) confirm the charter references `harvest-agent` so re-fetch is cheap and known.

**Tier routing (companion lever, from FEAT-124 — decision already reasoned there).**

## Rollout / restart expectation
- **B1 (RESPONSE_FORMAT core + WA §I + charter):** these are **injected into a session's system prompt at launch**. They take effect on the **next launched session**, or on the next turn only if re-injected — an already-running session does NOT retroactively adopt them. A **user restart re-launches** and picks them up. The saving accrues over the life of the *next* long session, not the current one.
- **Tier visibility flag (`cost-collect`):** takes effect **immediately** on the next `cost:collect` run (a read-only script, no session state).
- **Fable-gate (`decide()`):** wired live in `claude-runtime.ts`; takes effect for **sessions launched after the change ships** (the hook set is bound at session start). A restart applies it. Requires independent clean-room verify first.
- **Net:** nothing here changes a *currently running* orchestrator mid-session; the contract changes are prompt-injection, so they need a fresh/restarted session to bind, while the `cost-collect` flag is live at once.

## Companion requirement: pattern-detection must not depend on orchestrator context

**This is a requirement the relay-through (B) rollout must not ship without a plan for — not an optional note.**

**The risk (raised by the user).** A leaner orchestrator loses the thing that currently *lets it spot cross-lane patterns*. Today the parent holding full lane context is what surfaces observations like "five lanes parked work behind a turn end today," "three tickets leaked home paths the same way," "third lane in a row reported housekeeping instead of findings." Relay-through sheds lane-result prose from live context, so any pattern-spotting that depended on that prose being present is at risk.

**Why most of the signal survives anyway.** Those catches were driven by a **one-line fact/verdict per lane** — exactly what the compact handoff (B1) KEEPS. "Parked behind a turn end," "leaked a path," "reported housekeeping" are one-line outcomes, not report prose. The prose being shed is not where that pattern signal lives; relay-through preserves it.

**The real gap — detail-level synthesis.** What relay-through genuinely puts at risk is patterns visible only across report *content*: "these three failures share one root cause," "all misread the same bitmask," "the same off-by-one recurs under different symptoms." A pointer-only orchestrator will not know to harvest the detail, because **it does not yet know the pattern exists** — and the existing B1.3 retrieval triggers (harvest before you revisit / challenge / merge / implement a detail-dependent finding) do NOT cover "notice a pattern you did not know was there." That is the precise coverage hole.

**The required companion — make pattern-detection a mechanism over the durable record, not a side-effect of orchestrator context.** This is strictly more reliable than relying on a fat context (which compaction can drop anyway), and the project already has the exact shape: `arch:watch` (`scripts/arch-watch.mjs`, FEAT-056) re-derives ticket-recurrence clusters from the board on demand, and WA §Q already states recurrence "must be triggered, not remembered." **Extend that principle to BEHAVIOURAL recurrence:** a triggered pass that reads the accumulated **compact outcomes** (the B1 handoffs / Activity-log entries) plus the **Activity logs / cost ledger** and surfaces "N lanes did X this window" — parked work behind a turn end, reported housekeeping not findings, leaked a home path, misrouted a tier, etc. Modelled on `arch:watch` (read the durable record, cluster, surface as a question), it survives compaction and does not depend on any single session's live context.

**Rollout constraint.** Relay-through (B) removes lane prose from the parent; the behavioural-recurrence pass restores the pattern-detection capability over the durable record. B should not be considered complete until this companion is planned and scheduled to build alongside/after it. The detail-level synthesis hole above is the specific capability B must not silently drop. (Detail-level cross-report synthesis remains partly a harvest problem even with the pass — the pass surfaces *that* a behavioural pattern exists so the orchestrator then knows to harvest the shared detail; the two compose.)
