# BUG-157 — Orchard closes a live container session mid-turn and kills its background agents

- **Status:** OPEN — ROUND-4 fix built + self-verified (replaces round 3's broken frame-staleness bound). The close decision now reads CONTAINER GROUND TRUTH — a `/proc` scan for the live tool process, keyed by the `CLAUDE_STATION_EXEC` tag `reapExec` already uses — instead of timing frames; and `detach()` arms the close-on-detach fuse on EVERY path (the round-2 leak was an unarmed detach). Real-CLI verified: the 420s-silent-tool-call data loss is GONE (work runs 420/420 through a tab reopen+close despite 420s of frame silence) and the leak CLOSES (adversarial stuck-row 4/4, ~32s; container-revival data-loss variant 3/3). Independent clean-room verify REQUIRED (session-lifecycle + data-loss, regression-prone — fixes a data-loss + a leak that PRIOR rounds of this ticket introduced; BUG-043/044/072/074/105 lineage). Top items for it: the process-probe discriminator's edges (a non-Bash multi-minute zero-frame tool; an MCP server launched via `sh -c`), and the reap reschedule on a non-fuse close. Landed the "real container ground-truth liveness" slice of FEAT-109's intent in the bridge; the broker-in-container (drain gating, out-of-band delivery, re-adopt parity) remains FEAT-109's job.
- **Severity:** high (silent data loss — live agents and their unreported results are destroyed)
- **Area:** session lifecycle / background-work protection (`src/server/agent-bridge.ts`); the container arm specifically
- **Reported:** 2026-08-27 (round-1 lane diagnosed with ground truth; this is round 2 — the fix)

## Symptom
Orchard kills live sessions and their subagents. Confirmed on a container-project session (id `2eda4b9b-e115-4fa8-a551-88dcf94de9cb`): Orchard called `AgentSession.close()` ~15s before two working agents would have reported; both were killed 3ms apart after running 40s and 30s, and their results were lost mid-sentence. Two independent signals corroborated: Orchard's own `/running` and `/live` endpoints reported nothing driving, and `docker exec … ps` showed the container holding only `docker-init` and `sleep infinity`. Six real sessions across 1825 transcripts carry this signature; the four most recent are all container projects, all within three days — a live, accelerating, container-specific regression.

## The chain (re-verified against the code this round)
All in `src/server/agent-bridge.ts`:
1. **`busy` was turn-SOURCE-scoped, not turn-scoped.** It was set at exactly two sites — `start()` and `send()`. A turn the CLI STARTS ITSELF from a task notification (a "woken"/surfacing turn) never set it, so `!this.busy` was guaranteed true during precisely the turns this destroys. The detached-close fuse (`#armDetachedClose`) requires `!this.busy` to fire, and the empty-level arm in the `background_tasks_changed` handler requires `!this.busy` to re-arm it — so both fired mid-turn.
2. **`close()` EOFs stdin into the container CLI and hard-kills the exec.** `#runtime.close()` → `InputQueue.end()` sends stdin EOF into `docker exec -i`, which makes the CLI exit at its next turn boundary and take its background agents with it; and a 15s `reapExec` then hard-kills the container exec unconditionally. Observed close-to-kill gap: 3.78s.
3. **Container sessions had none of the protections built for `direct`.** `#survivalConfigured` is set only in the `direct` arm, so `survivable === false`, `processProbe()` is permanently `'unknown'` (no host pid to check), and the empty background level was trusted on its own with no ground-truth backstop.
4. **A SendMessage-revived retired task was invisible to `workLifetime()`.** BUG-105 deliberately keeps a re-announced (revived) task id retired — the row re-settles to its prior outcome and `#rebuildBackgroundLevel` filters it out of `#backgroundTasks` — so a revived agent counts 0 toward the background level and makes the session MORE closeable while it runs.

## Fix — A + B (this round; the durable class fix is FEAT-109)
### A — make `busy` turn-scoped, driven from the stream
`#markForegroundTurnLive()` sets `busy=true` (and stamps the turn clock, pushes the running snapshot) on `init` — the unambiguous turn-OPEN signal, which a task-notification-woken turn always emits (BUG-043 finding 5, real-CLI probed). `result` clears it exactly as before. This removes the `!this.busy` precondition for CLI-woken turns, so the fuse cannot fire mid-turn; it also fixes the collateral where a user message could be pushed into a turn Orchard believed was not running (`send()` now correctly throws "a turn is already running"). NOTE (round-2 verification): the first cut also pinned on main-thread `assistant`/`stream_event` frames; that re-set `busy` on a frame that trailed a turn's `result` and made a detached session never self-close (a leak `verify-detach` caught). Pinning ONLY on `init` fixed that while keeping the woken-turn protection — see the Activity log.

### B — make the container close conservative + cover the revival
- `#containerQuietToClose()`: a **positive quiet signal** the container close now requires. For a container session (no ground-truth probe) it demands NO frame for `CONTAINER_QUIET_TO_CLOSE_MS` (env `CLAUDE_STATION_CONTAINER_QUIET_MS`, default 10000) AND `#hasUnsettledWork()` false (no `running` agent row, no live revival). For a `direct` session it is vacuously true, so direct behaviour is unchanged (governed by the survival probe). `#armDetachedClose` now closes on an empty level only when this is true; otherwise it re-arms.
- The 15s stranded-`reapExec` in `close()` no longer hard-kills unconditionally: it reschedules (bounded, 8 attempts ≈ 2 min) while frames are still arriving within the quiet window — a container exec still emitting output is live work, not stranded.
- `#revivedTasks` (a `Map<id, when>`): a `task_started` for a task with an established outcome records the revival; `#retireTask` clears it; entries expire after `REVIVED_TASK_TTL_MS` (env `CLAUDE_STATION_REVIVED_TTL_MS`, default 300000). `workLifetime()` returns `'unknown'` (biased to detach per ARCH-002) while a revival is live, so `releaseSocketSession` detaches and the fuse re-arms instead of reaping a session whose revived agent is still working. This is a SEPARATE liveness signal read only by the close decision — it never touches `#backgroundTasks`/`#establishedOutcomes`/`#retiredTasks`, so BUG-105's row/level staleness guarantees are untouched.

## Why A and B are belt-and-suspenders (the empty-level open question)
Round-1 found `#backgroundTasks` empty at ~10:25:43 while an agent was demonstrably still working (it ran to 10:26:01, 22 tool uses). If the engine's level legitimately dropped the id, A alone (busy pins the woken turn) holds. If instead `#retiredTasks`/`#rebuildBackgroundLevel` retired it early, A treats a symptom and B is the backstop: `#hasUnsettledWork()` reads the bridge's own `running` rows independent of the level, so a still-working agent blocks the close even when the level has (wrongly) gone empty. The instrumented real-CLI repro to distinguish the two is in the round-2 verification (see the Activity log entry).
