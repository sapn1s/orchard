## Symptom
After a restart, Orchard re-attaches to a session that is still running (BUG-187).
If the user sends a message before that re-attach finishes, the message is never
delivered. The view first says "re-attached to the running session", as though
the message went in. It then shows: "this session is finishing after a server
restart and cannot take a new message yet (the re-attach is still completing) — it
retries when the session is free". Nothing retries it, and the text is not handed
back to the composer.

## Repro
Seen in `verify-bug-072-delivery-visible` when its planted survivor could be
adopted and its fake CLI did not answer the re-initialize, so the adoption stayed
`pending` for 30 s. Two sends in that window each got this sequence on the socket:

```
{"t":"ack","of":"start","reattached":true}
{"t":"error","message":"this session is finishing after a server restart and cannot take a new message yet (the re-attach is still completing) — it retries when the session is free","fatal":false}
```

The engine input log received 0 of those 2 messages, and neither reached the
transcript. With a real CLI the `pending` window is short, but the same gate also
refuses while an adoption is `responder-only` and the broker is not deliverable
(its lifetime is not `yes`). That state can last for a whole drain.

## Expected
The refusal is retryable and reaches the client before any ack. The client's
BUG-045 path then queues the message, shows the waiting chip and retries it. If
that is not possible, the text goes back to the composer (BUG-029). A message the
server did not deliver must never be acked as delivered.

## Context pack
- `src/server/index.ts`, the `start` + `resumeSessionId` reattach branch (`running.attach(send)` … `if (cmd.prompt) { … running.send(cmd.prompt) } catch → { t:'error', fatal:false }`). The ack is sent before `send()` is attempted, and the catch drops the `retryable` flag that `send()` sets on the error.
- `src/server/agent-bridge.ts` `send()`: the BUG-187 B2 gate for `#adoptState === 'pending' | 'responder-only'` (`#responderOnlySendGate`).
- `public/app.js`: the idle-reattach branch of the `ack` handler, which calls `settleDrainWaitDelivery()` and clears `pendingStart`. The `error` handler queues a retryable refusal only while `pendingStart != null`, so an error that arrives after the ack falls through to `say()`.
- Related: BUG-187 (B2 gate), BUG-045 (retryable queue), BUG-029 (composer hand-back), BUG-072 (where it was found).

#### Plan

**Root-cause fix: decide the gate before anything is acknowledged. A refusal is always retryable and always reaches a client path that keeps the text.** The queue is the one that already exists and already holds a message durably: the client's BUG-045 drain-wait queue (visible chip, persisted by BUG-129, retried by a full `start` that the server judges again, and retired only on an ack).

- **Why not a server-side queue-until-adopted?** I considered it and rejected it.
  - A queue in `AgentSession` memory dies with the server, and "the server restarts again mid-queue" is one of the named failure modes. The only copy that survives a restart is the tab's.
  - A server-held message would also need a second ack protocol (queued now, delivered or failed later) and a way to hand the text back when it fails. BUG-045/029/129 already built both on the client.
  - It would be a second place able to hold the same message (ARCH-010).
- **The bound.** The `pending` window is already bounded by `#completeAdoption`: 30 s init + 5 s reclaim, then `adopted`, `responder-only` or `failed`. `responder-only` lasts until the old broker's drain ends. The row stays visible for that whole time and names why, and the user can edit, discard or pull it back to the composer at any time (BUG-132/149 affordances). So the message is never silent and never stranded behind an invisible wait. I am deliberately **not** adding a wall-clock give-up that marks the row dead: a drain held by a live lane is legitimately long (BUG-159 is the precedent: "HELD, never refused").

**S1: `agent-bridge.ts`.**
- Add a public `sendGate()`. It returns `{ok:true}` for any session that is not adopt-gated. For `pending`/`responder-only` it returns the B2 verdict plus a `drain`-shaped payload read from the same broker record: `{adoptState, why, backgroundLive, backgroundTaskIds, backgroundLifetime, drainHeldSince, heldForMs, brokerState}`.
- `send(prompt, gate = this.sendGate())` acts on the verdict it is given. That lets a caller that already decided (S2) hand over that same decision, so there is no second read of a file another process writes. The one fact is decided once, and the decision is acted on once.
- The retryable throw also carries `drain`.
- The gate logic itself is unchanged: B2's conditions are exactly as BUG-187 set them.

**S2: `index.ts` reattach branch.** When the start carries a non-empty prompt, evaluate `running.sendGate()` **before** `running.attach(send)` and before the ack.
- If it refuses, return `{t:'error', fatal:false, retryable:true, message, drain}`. There is no attach and no ack, so the socket is not bound, and the client's BUG-045 path (`queueRetryableRefusal`) takes the text.
- If it passes, keep today's order (attach, ack, replay, then `running.send(prompt, gate)`). The post-ack catch keeps its non-retryable shape. Only `closed`/`budgetStopped` can throw there, and both are pre-existing and visible.
- A **promptless** reattach (BUG-160) is unaffected: watching a pending or responder-only session stays allowed.
- `busy` + `pending`/`responder-only` is also refused before the ack. Today it acks `busy` and the client re-queues for a boundary `send` that the gate would then refuse (path 2).

**S3: `index.ts` `case 'send'`.** Catch the throw locally. A retryable refusal goes out as `{t:'error', fatal:false, retryable:true, of:'send', message, drain}`, with no ack. Anything else is rethrown to the existing catch-all (unchanged).

**S4: `events.ts`.** The error event gains the optional `of?: 'send'`. `drain` gains the optional `adoptState?` and `why?`.

**S5: `public/app.js`.**
- In the `error` handler, add a branch ahead of the `pendingStart` one: `e.retryable && e.of === 'send'` → `queueRefusedSend(e.drain)`.
  - It takes the undelivered text from `pendingSend` (the `submit()` path, with its exact bubble element), or else from `outbox.texts` (the `flushQueue`/`deliverForced`/behind-background batch: one row per original item, so a batch is not flattened).
  - It removes the phantom bubble and clears `outbox`/`pendingSend`.
  - It pushes the rows as drain-wait rows for this session's sdk id, at the FRONT of the queue so their order is kept.
  - It closes the socket (`ws=null`, `live=false`, which is the same reason as in `queueRetryableRefusal`), sets `resumeOnNextSend`, and arms the retry.
  - The retry is the ordinary BUG-045 `start` + resume, so it goes back through S2's gate.
- When `drain.adoptState` is present, the drain-wait chip (`heldWhy`, `app.js:11457`) and the queued `say()` name the real reason: "the session is re-attaching after a server restart / is finishing an earlier server's drain". The generic "the session is mid-reply" does not apply there.

**Interaction with BUG-187 (adoption, refusal floor, backstop).**
- Nothing about adoption itself changes: the gate's conditions, `#completeAdoption`, reclaim, the request floor, the lane-stop bound, the close gate (B4) and the ledger are all untouched.
- The only BUG-187 behaviour that changes is *when* the B2 refusal is decided (before the ack, not after it) and *how* it reaches the client (retryable, instead of flattened). The ticket's "changes BUG-187 behaviour" is exactly this, and nothing more.
- Not attaching on a refused prompt-bearing start means that socket never becomes the session's `#emit` sink. So the detached-close fuse and B4 see the same state as before the start. The client then closes its socket, and nothing ever attached, so `releaseSocketSession` has nothing to release.

**Interaction with BUG-065/072 (survivor delivery) and BUG-045/029/129.**
- FEAT-065's delivery branch is reached only when no in-memory bridge exists (`running` undefined), so S2 does not touch it.
- After a failed adoption (the bridge is closed without a reap), the next retry falls through to the existing survivor path. If the broker is draining, idle and deliverable, FEAT-065 delivers (H7 accept, then ack). Otherwise it refuses retryably (`refuseDrainHeld`), and once the broker is gone the retry resumes from disk.
- BUG-072's rendering of delivery mode is unchanged.
- Exactly once:
  - the server refuses before any byte reaches the CLI;
  - the row leaves the queue only on an ack (`settleDrainWaitDelivery`);
  - `flushQueue` skips the in-flight attempt's row;
  - a `busy` reattach-ack moves the row into the boundary queue exactly as today.

**Failure modes (each gets a verifier arm).**
- **The adoption fails:** P2. The CLI never answers the re-initialize, so the 30 s adoption timeout ends in `failed` with no reap. No attempt is acked-then-refused, and the message is either delivered exactly once or is still a retryable, visible row.
- **The adoption times out:** the same path as P2. The timeout *is* the failure.
- **The server restarts again mid-queue:** the row lives in the tab, and the retry loop re-attempts against whichever server answers, where S2 applies again. A reload restores the row `dead` (BUG-129: never auto-resent, recoverable in one click). That is visible, not lost.
- **A duplicate send:** covered by the exactly-once argument above. P1/P3/B1 assert the CLI got the text **once** across all attempts.
- **UI feedback:** B1 (brave). The typed text becomes a drain-wait row (no bubble claiming delivery), and it retires on delivery.
- **Responder-only path:** P3 (start path), then eventual delivery once the old CLI exits and the retry resumes from disk. P4 covers the attached-`send` path.
- **Residual window (proposed as S6; the reviewer should say whether it is in scope).** After the gate passes, `send` writes a raw user frame through the attach facade. If the broker ends the CLI's input between the gate's status read and that write, the broker drops the frame and answers with an **id-less** `deliver_ack accepted:false` (`session-host.mjs:746`). `BrokerChannelImpl.onLine` (`survival.ts:332`) ignores that ack. That is a silent loss in a window of milliseconds.
  - Proposed S6: the channel surfaces an id-less reject to the bridge, and the bridge emits `{t:'error', retryable:true, of:'send', drain}`. The client's `pendingSend`/`outbox` are still held, because no `turn-end` has come, so S5 re-queues it.
  - An OLD (pre-protocol-2) broker has no H7 and drops such a frame with no signal at all. That residual cannot be fixed server-side, and it is transitional.

### 2026-09-27 — plan re-review — openai codex (default), run 01a0e2e3-02dc-7cc1-8c33-edbc04ed9fbc — VERDICT: REJECT; disposition (round 1c, final plan)

The re-review found R1 (correlated acceptance) and R3 (per-attempt ownership) sound. It gave five more REQUIRED changes. I accepted four and refuted one in part:

1. **The ghost retry contradicts the tri-state rule. Accepted.** A ghost attempt is one whose socket died with no ack and no refusal. It now becomes a **DEAD** row ("not confirmed — check the transcript before sending it again") and is never re-sent automatically.
2. **Substring matching against the transcript cannot prove that an attempt was delivered. Accepted.** The new paths use **no transcript judgement at all**. An `uncertain` outcome and a ghost attempt both keep their uncertainty and go to a DEAD row, which is visible and one click to resend. BUG-129's existing reload judgement is not touched.
3. **The reservation's lifetime. Accepted.** A module-level `deliveryInFlight: Map<sdkSessionId, socketToken>` is acquired **synchronously, before the await**. It is checked at the top of *every* resume route:
   - a prompt-bearing start gets a retryable refusal;
   - a promptless reattach gets `live-elsewhere`;
   - the survivor fallback is reached only after this check.

   It is released in `finally` once the delivery settles, and never by a socket close. Tests cover contention, a disconnect during delivery, and the bridge closing during the await.
4. **The old broker could bypass the refusal through the `adopted` state. Refuted in part, with evidence.** The gate exists because a `responder-only` broker's drain was decided by *another* server. An `adopted` old broker was confirmed via `confirmAdoption()`: this server owns it and alone can end its input, exactly like a broker it spawned itself (`agent-bridge.ts` `#completeAdoption`, the "older broker that was still running — adopted" branch). Its raw-frame path is therefore the same as every spawned session's, and it does not race a foreign drain decision. The FEAT-065 old-broker write (`survivor-delivery.ts:334`) **is** refused (P7 asserts zero prompt writes).
5. **Proof. Accepted.** Added arms: reservation contention; a delivered reattach that must get `busy:true` + `promptDelivered:true`, where the client must settle it and not transfer the row; and an **acceptance-then-lost-ack** browser arm. That arm closes the tab's retry socket right after it sends `start`. The server delivers into a closed socket, the attempt ghosts, and it must end as a DEAD row with exactly 1 delivery. `promptDelivered` is emitted only after `deliver_ack accepted:true` and takes precedence over the busy row transfer.
