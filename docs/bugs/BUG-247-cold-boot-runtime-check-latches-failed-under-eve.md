# PLACEHOLDER — short title

## Problem

After a cold reboot, new host sessions were refused with the block "runtime check failed: the bundled runtime did not run `--version` at boot. Restart Orchard to apply; sessions already running are unaffected." A restart cleared it, so it looked transient, but it recurred on every cold boot.

## Diagnosis

`src/server/runtime/runtime-update.ts`: the one-time boot check `bootChecked` (module-load IIFE, ~line 383) calls `probeVersionAsync(bin)` (~line 248), which spawns `claude --version` and arms a 5 s `setTimeout` guard. On a cold boot the SYNCHRONOUS half of server startup blocks the event loop for longer than 5 s. When the loop resumes, Node runs the timers phase BEFORE the poll phase, so the long-expired timeout fires `finish(null)` and SIGKILLs the child even though `claude --version` had already exited 0 during the block — its `close` event was waiting in poll. `probeVersionAsync` resolves null, `bootState` latches `'failed'`, and `admission()` refuses every new host session for the life of the process (a failed boot check never becomes a baseline — by design).

## Fix

In `probeVersionAsync`, distinguish a real timeout from loop starvation by measuring how LATE the timer fired relative to its scheduled fire time. On fire, if `late > SLACK_MS (500)` and `rearms < MAX_REARMS (5)`, the LOOP was starved (not the child): re-arm a fresh full `timeoutMs` window and let the pending `close` resolve in the same iteration's poll phase. Otherwise kill the child and `finish(null)`. A genuinely hung binary re-arms at most 5 bounded windows — each a real timeout window the loop is NOT starved through — then fails closed in bounded time. Hung / exit-1 / garbage-output binaries still fail. Deliberately NOT a `setImmediate` deferral: starvation can exceed any single deferral. Comment cites BUG-247.

## Out of scope (recorded)

`validateRuntimeImage` (`src/server/container-manager.ts` ~3102) spawns `--version` with the same wall-clock `setTimeout` shape, but it is NON-LATCHING (it runs per-admission, not once at boot), so a starved timeout there self-corrects on the next admission. Left untouched.

### 2026-10-09 — fixing lane r3 (design review + redesign by construction)
- **design decision — (2a) child-relative timeout, alone.** The boot proof is now `probeVersionSync`: `spawnSync(bin, ['--version'], { timeout: 5000, killSignal: 'SIGKILL', stdio: ['ignore','pipe','pipe'] })`, accepted iff `!r.error && r.status === 0` and a version parses. spawnSync runs the child on its own private libuv loop, measures the timeout from the child's spawn and returns synchronously, so there is no main-loop timer and starvation cannot reach the verdict. - **Q1 threat model.** The path is `node_modules/@anthropic-ai/claude-agent-sdk-<plat>/claude`, written only by npm or `updateHostRuntime`, both running as the service user. Putting a FIFO, socket or device node there requires write access to that tree as the service user (or root), and such an actor can already edit `src/server/**` and own the server. npm never produces one: its tar extraction keeps files, dirs and (where allowed) links; it does not create FIFOs or device nodes. **Non-adversarial blocking producers:** (i) a hung NFS/SMB/FUSE mount or a failing disk under `node_modules`. No async containment in this module can help, and a dying local disk returns EIO eventually (the hash goes null, fails closed, stays retryable). (ii) A symlink from the binary path to a char device such as `/dev/zero`: also non-npm, and it makes the hash stream spin forever (CPU) rather than block. **Disposition:** the adversarial FIFO is OUTSIDE the threat model (RESCOPE), but a containment is cheap and also fixes the thread leak on both arms, so contain it.
- **Q2 one containment: non-blocking open plus fstat, regular files only, in the ONE `hashFile` helper.** Every hash caller goes through it: boot `identifyBinary`, retry PRE `identifyBinary`, admission `ensureHash`. Checking the fd, not an `lstat` of the path, closes the lstat→open rename race.
