# FEAT-157 — projects pin a versioned Orchard base and hear about new ones

## Symptom
The user asked for this: Orchard owns one universal container build, and each project adjusts it for its own needs. When Orchard finds a problem with that build, it should publish a new version but not push it into projects silently. Instead each project's orchestrator gets a message saying an update is available, and can adopt it or mark it skipped.

Today there is no version and no message. When Orchard's build changes, every container project quietly moves onto the new build at its next launch, whether or not that project was ready for it. And when nothing in the build's definition changes, security patches to the operating system underneath never arrive at all.

## What exists vs what is missing (checked against the code at a977e76, 2026-09-29)

The orchestrator's hypothesis, point by point.

- **Layering: CONFIRMED, with a correction on who it applies to.** Orchard builds `claude-station-base:u{uid}-g{gid}-{hash}` from `src/server/container/Dockerfile` + `provision.json`. A project Dockerfile must build `FROM ${ORCHARD_BASE_IMAGE}` (the linter in `src/server/project-dockerfile.ts` enforces it), and the base reaches that build as an exported OCI layout (`baseOciLayout`). But this machine has 6 container projects: 1 builds its own Dockerfile, 5 run the base directly, 0 use a prebuilt image. A prebuilt `container.image` bypasses the base entirely: Orchard does not build it, cannot update it, and can only tell that project about a release.
- **(a) No declared version: CONFIRMED.** A base is identified only by a content hash (`provisionHash()` in `src/server/provisioning.ts`, sha256 of the Dockerfile + provision.json, 12 hex chars) placed in the tag. There is no version number, no changelog and no security marking. `provision.json`'s `manifestVersion: 1` is the file's schema version, not a base version.
- **(b) Projects float: CONFIRMED, and it is worse than stated in three ways.**
  1. The float is real. A changed base definition produces a new tag. A project using the base directly then sees `image … != …` in `driftReasons` and its container is recreated at the next `ensureContainer`. A Dockerfile project has the base id inside its own image hash (`dockerfileHash(…, { baseTag, baseId })`), so it rebuilds, and the swap waits until no session is live.
  2. **From reading the code (not run):** a project using the base directly gets NO wait for live sessions. `deferImageSwap` holds back an image-only change only when `locked` (a Dockerfile project, `container-manager.ts` ~L2076). So a base bump plus a new session launched in a project that already has a live session removes the container under that live session. FEAT-151's "a bump never force-restarts a running container" is true only until the next launch in that project. This needs its own BUG ticket and a probe to confirm; it is not in this feature's scope.
  3. **Security patches never arrive through the float.** `ensureStationImage` returns early when the tag already exists, and the Dockerfile is `FROM ubuntu:24.04` plus unpinned `apt-get`. The OS packages are frozen at whatever day the image was first built, until someone edits the definition or presses Rebuild. And Rebuild on a Dockerfile project does not rebuild the base at all: `ensureDockerfileImage` calls `ensureStationImage` without `force`.
  4. **A pin is impossible today, even by hand.** Old bases are not kept. `pruneSupersededImages` deletes every unused old tag after each build, and the source of an old version is gone the moment Orchard's tree moves on. Right now 3 base tags coexist on disk (1.1 GB, 3.0 GB and 3.1 GB) only because containers still reference them.
- **(c) No notice path: CONFIRMED, but a carrier exists to reuse.** `src/server/decisions.ts` (FEAT-029) is a per-project decision store: persistent, crash-safe (`writeAtomic`), rendered as Needs-You rail cards, and it already carries typed payloads (`gitWrite`, `services`) under the rule that a record does nothing until someone answers it. For an open session, `boardAnswerBriefing`/`takeBriefing` show the pattern of saying something once, on the next turn, without starting a turn.
- **(d) No policy: CONFIRMED.** Nothing exists.
- **A constraint the hypothesis missed, and it shapes the design.** The Claude CLI is baked into the base (FEAT-151), and it has to match the version bundled in the host SDK: *"SDK JS and CLI ship version-locked."* A project pinned to an old base would therefore also pin an old CLI. The first host SDK update would mismatch them, and that project's container sessions would break. **The CLI cannot be part of what a project pins.**
- **ARCH-020 is orthogonal: CONFIRMED.** That ticket is about isolation between projects on the shared build daemon. This one is about versions over time. They touch at one point: `baseOciLayout` keeps exactly one exported base and deletes the others. With several versions pinned at once, that export has to be kept per version, or two projects on different versions will keep deleting each other's export.
- **The guide an agent gets: NONE.** `src/server/templates.ts` does not mention containers or Dockerfiles anywhere. A project's agent learns what its Dockerfile may do only by being refused.

## Design (revised 2026-09-30, round 1 build lane — folds in all 12 adopted review findings; the round-1 text is at `git show a977e76:docs/bugs/FEAT-157-*.md`)

**Invariant.** Which base a project runs is a fact the project declares (the *desired* pin). What it actually runs is a fact the container runtime reports (the *observed* artifact). Orchard never moves the desired pin silently. The one exception is a security release: it raises the *target* above the pin, is applied at the next launch with no live session, and is never applied under one.

### Where each fact is declared (ARCH-010)
| Fact | Owner (written once) | Readers |
|---|---|---|
| Base releases, their class, changelog, `adjust` text, recipe hash, security package checks | `src/server/container/base-releases.json` (committed, append-only), with each release's recipe snapshotted in `src/server/container/releases/v{N}/{Dockerfile,provision.json}`; cut by `npm run base:release` | `src/server/base-releases.ts` (strict parser; a torn/corrupt file is an error, never "no releases") |
| A project's desired pin, skipped and deferred versions | `settings.container.base = { pinned: N \| "dev" \| "legacy:<tag>", skipped: [N], deferred: { version, until } \| null }` in the registry, project scope only | `basePinOf(project)` |
| The security floor and the target a launch builds | `baseTarget()` in `base-releases.ts` — ONE policy function every settings, answer and launch path calls (finding 6, 10) | ensure, rail, agent route, guide |
| What a container actually runs | the image labels on the container's image (`claude-station.base-version`, `claude-station.cli-version`), read from docker | notice, guide, status (finding 2, 10) |
| The Claude CLI a container needs | the host SDK's boot-proven bundled binary (`runtime-update.ts` `BOOT_CLI_VERSION` + `BOOT_IDENTITY.hash`) | runtime layer |
| The Dockerfile/image rules an agent is told | the tables the enforcing code reads (`RESERVED_ENV_RULES`, `LOCKDOWN_RULES`, `BUILD_RULES`) | `containerBuildSection()` |

`track` is dropped: one field, `pinned: N | "dev"` (finding 10). "Latest" is never stored per project; it is read from the catalog.

### Releases and what a release freezes (finding 1)
- A release entry: `{ version, date, class: "security"|"fix"|"feature", summary, adjust, hash, verify? }`. `hash` is the recipe hash of the snapshot. A security release must carry `verify: [{ package, minVersion }]`.
- Image identity is the version, not the recipe: `claude-station-base:v{N}-u{uid}-g{gid}`, labelled with version, recipe hash and owner. A dev build is `claude-station-base:dev-u{uid}-g{gid}-{hash}`.
- A release is built once per machine and then KEPT: the image id first built for each version tag is recorded in `base-artifacts.json` (data dir). A later rebuild (the image was removed) is from the snapshot and is recorded and shown as "same recipe, not same bytes".
- A security release builds with `--no-cache --pull` and must prove each `verify` package reached `minVersion` (`dpkg --compare-versions` inside the built image), or the build fails.
- Unreleased changes to the working-tree definition reach only `pinned: "dev"`; no other project sees them and no notice is sent.

### The CLI runtime layer (fork 1 = A; findings 4, 5)
- The base no longer contains the Claude CLI. The CLI is a one-file layer Orchard adds on top of whatever the project runs on (the pinned base, or the project's Dockerfile image).
- **Structural, no build step.** The layer is made with `docker create` (never started) + `docker cp` of a one-entry tar (the binary at `/home/claude/.local/bin/claude`) + `docker commit`. No instruction from the parent runs (no ONBUILD, no RUN, no shell, no network), USER/PATH/SHELL/ENV are untouched by construction, and the parent's layers are a byte-identical prefix of the result.
- **Source:** the host SDK's own bundled binary, copied and hashed; its sha256 must equal the boot-proven `BOOT_IDENTITY.hash`, so the container CLI is exactly the one the loaded SDK JS speaks to (the npm `claude-code` binary and the SDK's bundled one have the same BuildID, measured). No registry fetch. The `claude-code` pin leaves `provision.json`; the Runtime pane's "container pin" becomes read-only.
- **Identity:** `claude-station-rt:{cliVersion}-{key}`, key = sha256(parent image id, CLI sha256, uid, gid, arch). Labels: runtime marker, CLI version + sha256, parent id, owner.
- **Validation:** a real stream-json session handshake in the new image (offline, `--network none`, under the run-time lockdown): the first frame must be `system/init` with `claude_code_version` equal to the host's. `--version` alone is not accepted.
- **Legacy images** already carry a CLI (label `claude-station.claude-version`). If it equals the host's, the image is used as is (no layer, no recreate); otherwise it is layered.
- **Never launches mismatched:** if the container must change because the CLI changed and sessions are live in it, a NEW launch is refused (`cli-mismatch-live`, with the versions and the fix) rather than started on the mismatched container; live sessions are untouched. While the host runtime is skewed (SDK updated on disk, restart pending), no new layer is built; an existing one for the boot CLI is still used.
- Prebuilt `container.image` projects are not layered (not Orchard's image); their notice is informational.

### Notices: derived by the server, never stored as their own truth (findings 7, 8, 10)
- A notice is **computed** on read from (catalog, the project's pin, the observed artifact, now). There is no store, no create route and no HTTP way to make one: forging is impossible by construction, a crash cannot tear one, a stale one cannot linger, and an expired deferral reopens by itself (no timer needed).
- Identity: `id = base:<projectId>`, `rev` = a hash of (from, to, class, observed, deferral). The notice lists versions by reference; the card and the briefing read the entries from the catalog.
- **Rail:** a `baseUpdate` item on the project's Needs-You rail: from → to, class, the entries between them with their `adjust` text, and state (pending apply, build failed, escalated). Buttons: Adopt / Defer 7 days / Skip; no Skip for security; prebuilt: informational, no buttons.
- **Open sessions** get it once, on their next turn (a `[station]` briefing, seen-set per session keyed by `id@rev`); nothing starts a turn.
- **Later launches** get it in the first-turn briefing. The static guide rides in the system prompt (byte-stable, FEAT-113); the volatile part (observed version, pending notice) rides in the first turn.
- **Answering:** `POST /api/projects/:id/base-update` (rail) and `POST /api/sessions/:sid/base-update` (agent; project taken from the live session, never from input). Both name `{ action, version, rev }` and are refused (409) if `rev` or `version` is stale. The generic answer route refuses `base:` ids. `container.base` is not writable through the settings PATCH at all. The agent CLI (`npm run base -- status|adopt|defer|skip`) calls the session route with `ORCHARD_SESSION`. Limits, stated: the HTTP API has no per-caller auth (the pre-existing residual), and a container session cannot reach the host API, so a container project's agent relays to the user.

### Adopt / defer / skip, and the security floor (findings 2, 3, 6)
- **Adopt** writes the desired pin (`pinned := N`). The observed artifact changes at the next launch with no live session (BUG-214's defer path, reused — no second one). The notice stays open ("adopted vN — applies at the next launch with no live session", or "build failed: …") until observed = target.
- **Defer** sets `deferred = { version, until = now + 7 days }`; the notice is hidden until then.
- **Skip** adds N to `skipped`; N is not re-noticed; a later N+1 notices again and lists everything from the pin, N included.
- **Security:** `baseTarget` = max(pin, newest security release above it). Skip is refused (409) on both routes; Defer is accepted as an acknowledgement but does not delay the apply. A launch builds the target; if that build fails, **new launches are refused** (`security-update-failed`) and live sessions keep running. Under live sessions the swap waits (never kills). After 7 days unapplied the card escalates. Adopting an intermediate version below the floor is refused. Moving to `dev` needs the user route.
- Limits, stated: a project Dockerfile can reinstall vulnerable packages; prebuilt images are not managed.

### Garbage collection (finding 11)
Base and runtime images are collected by artifact identity. Kept: every registered container project's wanted base and runtime image, images any container uses (docker refuses anyway: never `--force`), in-flight builds, and last-good Dockerfile images. Removal is by inspected id, own-owner only (BUG-218 rules unchanged). Base OCI exports for Dockerfile builds are kept per base image id and removed only with their base image.

### The guide the per-project agent gets
`containerBuildSection()` in `templates.ts`, for `isolation: container` projects only, generated from the enforcement tables: reserved env keys (`RESERVED_ENV_RULES`, which `reservedContainerEnvReason` iterates), the run-time lockdown (`LOCKDOWN_RULES`, which `lockdownCreateArgs` flattens), and the build facts (`BUILD_RULES`). Adding a rule to a table changes both the enforcement and the guide; nothing restates it. It also says: never install the Claude CLI (Orchard layers the host's).

### Migration for existing projects (finding 9; replaces the round-1 steps 2–3)
1. Cut **v1** = the base definition at ship time (CLI removed), with its snapshot.
2. Once per project (journal: `base-migration.json` in the data dir; `registry.json` backed up first), a container project with no pin gets:
   - a station project whose container runs `claude-station-base:<tag>` → `pinned: "legacy:<tag>"` (exactly what it runs; nothing rebuilt or recreated);
   - a Dockerfile project → `legacy:<tag>` of the base its image was built on (read from the image's inherited `provision-hash` label), so its image hash, and its container, are unchanged;
   - a project with no container at all → the newest release (nothing to preserve);
   - a prebuilt-image project → no pin (not Orchard's image).
3. Restartable: each project is written atomically and the journal records it; a crash leaves the rest for the next boot. A project already in the journal whose pin is later missing or unreadable enters **recovery**: it keeps running its current container, launches only into it, and the rail says so. Recovery never adopts.
4. The rail then offers v1 to every legacy project ("one-time restructure: the CLI moves to a layer; your container is recreated at the next launch with no live session"). Nothing moves until someone adopts it, except a CLI change, which layers the legacy image (a CLI-only recreate at an idle launch).
5. New container projects are pinned to the newest release at creation.

## Decision — how does the Claude CLI stay current while a project pins an older base?

- **A — Runtime layer on top of the pinned base.** Orchard adds a thin CLI stage over `base:vN` (station) or over the project's final stage (Dockerfile). The pin freezes the OS and toolchain; the CLI always matches the host SDK. A CLI bump rebuilds one thin layer. Cost: the image build becomes two steps, and the project Dockerfile build needs a final stage appended.
- **B — Bind-mount the host's CLI binary into the container.** No CLI in any image at all, and version skew is impossible. Cost: the SDK's bundled binary was built for the host's C library and is untested on Ubuntu 24.04; the bind becomes something that triggers recreation on every SDK update; and it undoes FEAT-151's decision to bake the CLI.
- **C — Keep the CLI in the base; every CLI bump is a mandatory base release.** The simplest option. Cost: CLI bumps are frequent, so a pin rarely holds for long. The feature shrinks to today's float plus notices, and projects rebuild their whole stack on every CLI bump.

Recommended: A. It is the only option where the pin means what it says and the CLI cannot mismatch the host. B is worth a probe (does the host binary run in the container?), but it depends on a C-library compatibility fact nobody has checked.

**Decision: A — the thin Orchard-added CLI layer on top of the pinned base (orchestrator, 2026-09-29, per the user's standing "do what you recommend").**

## Decision — can a project ever refuse a security release?

- **A — No; applied at the next launch with no live session, never under one.** Defer is allowed only until that launch; the card escalates after 7 days of never reaching one. The orchestrator's default.
- **B — Yes, but only by the user, with a reason and an expiry.** A user-only waiver (the rail card, not the agent CLI), recorded in the project's config; it expires and re-arms. Cost: a vulnerable base can persist, deliberately.
- **C — Applied immediately, recreating even under live sessions.** Rejected as the default: it destroys running work, which is BUG-157's data-loss class.

Recommended: A, with B as a later addition only if a real project needs it. The user decides; the agent CLI can never skip a security release under any option.

**Decision: A — no refusal; once a security release is due and its build fails, block new launches, and never kill a live session (orchestrator, 2026-09-29, per the user's standing "do what you recommend").** B (a user-only waiver) stays a later addition only if a real project needs it.

## Proof bar (revised 2026-09-30 — finding 12)
Must-FAIL baselines are fixed, never HEAD: the a977e76 tree and the lane's pinned pre-lane snapshot (`scratch/feat157/prelane/`, sha256-listed). All docker work runs in the FEAT-158 sandbox under its lock.
1. **(1a)** An unreleased working-tree base change leaves a pinned project on its base with NO notice. **(1b)** A cut release leaves it on its base WITH a notice. Pre-change: the container is recreated onto the new base.
2. **Adopt** applies at the next launch with no live session and waits under a live session, for a station and a Dockerfile project.
3. **Skip** a feature release: nothing rebuilt, no re-notice; release N+1 notices again listing N and N+1.
4. **Security:** Skip refused (409) on the rail route and the agent route; applied at the next idle launch, never under a live session; the package check proves the version moved; a failed security build refuses new launches and leaves live ones running; an intermediate adopt below the floor is refused.
5. **CLI layer:** only the one-file layer changes on a CLI change — the parent's layer digests are a byte-identical prefix; the handshake reports the host's version; a CLI change with live sessions refuses the new launch and kills nothing.
6. **Reaches a project not running:** its next launch's first turn carries the notice and its system prompt the guide; an open session is told once. The rail card in a real headless browser, both themes, over a synthetic busy fixture (several projects, one security, one prebuilt), labelled synthetic.
7. **Truncated reads:** `base-releases.json` and `registry.json` truncated at several points: no crash, no adoption, no float; the launch keeps the current pin and the error is visible.
8. **Pinned image missing:** rebuilt from `releases/vN/` and recorded as "same recipe, not same bytes"; snapshot also gone: an honest error, never a move to the newest.
9. **Guide derived:** adding a rule to each enforcement table changes enforcement and the guide with no other edit.
10. **Forged / stale / cross-project:** a needs-you raise cannot carry a `baseUpdate`; the generic answer route refuses `base:` ids; a stale `rev`/`version` answer is refused; the session route acts only on the session's own project.
11. **Migration:** legacy pins written, no container recreated (container ids unchanged), no history touched, a crash mid-migration resumes; a missing pin after migration enters recovery.
12. **GC:** a pinned version and an in-flight build survive a prune.
13. **Anti-regressions:** `verify-bug-214-218-base-lifecycle`, `verify-bug-107-image-staleness`, `verify-bug-216-*`, `verify-feat-155-image-env-policy`, the FEAT-151 suites (adjusted where option A superseded the provision.json pin), `npm run gate`, `board:check`.
14. **Independent clean-room attack**, one attacker per property, concurrently, jailed to the sandbox: (a) a pinned project never changes base silently; (b) a security release cannot be skipped and never kills a live session; (c) only the server creates notices and an agent acts only on its own project's; (d) the CLI stays matched to the host under a pin; (e) migration recreates nothing and loses no history.
