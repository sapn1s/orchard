# ARCH-006 — line-ending normalisation is owned per-renderer, so any renderer that forgets it silently hides or deletes content

- **Status:** OPEN — NEEDS A HUMAN DECISION (3 options below). **No build starts until an option below is chosen.** Recommended: B — the mechanical check is the only option that makes the property observable at commit time, is the cheapest real improvement, and is a strict step toward A if A is later chosen; A is the elimination but costs an audit of every entry point, and C is priced below against three instances found in a single day.
- **Severity:** medium. Deliberately not higher: this is a single-user local tool, nothing is deployed, and none of the three instances was a security issue — no boundary between users, no other person's data. Deliberately not lower: two of the three **silently hid or deleted content the reader was meant to see**, with no error and no gap to hint at the loss, which is this project's own stated worst failure class — a thing that is wrong while every check passes.
- **Area:** frontend renderers that turn untrusted text (model output, transcripts, file bytes) into DOM — `public/lib/dom.js` (`prose()`), `public/lib/digest.js`, `public/lib/response-blocks.js`, and any future sibling.
- **Reported:** 2026-08-18, promoted from BUG-109's Deeper-flaw note (Candidate-yes), which correctly declined to file the ARCH from inside a fix lane and handed the class forward to the orchestrator.
- **Recurrence evidence:** FEAT-091 (two instances — `response-blocks.js` per-line predicate split on LF only; then `digest.js` on its own entry path, found by a generated corpus once the first was fixed), BUG-109 (`dom.js` `prose()` — normalised CRLF but not a lone CR, so a fence info-string strip ran past the break and deleted a whole code line). Three instances, one root, all found within hours of each other.

## Violated invariant

**No renderer's line-shaped rule may observe a line break that its own line-splitting has not already accounted for** — equivalently, every renderer sees text in which `\r\n` and a lone `\r` have both been collapsed to `\n` before any rule keyed on `\n` runs.

That is testable as stated, and testable two ways with very different strength. Behaviourally: for any renderer R and any input, R's output on that input must equal its output on the same input with every `\r\n` and lone `\r` rewritten to `\n` — the line-ending must be invisible to what renders. Mechanically: no module that contains a line-shaped rule (a split, a `replace`, or a regex anchored on `\n`, `^`, or `$`) may run that rule before it has normalised `\r\n?` at its own entry. Every ticket in the recurrence evidence is a different renderer breaking the same sentence. That is what makes this a class and not three bugs.

## The design that produces this class

Text enters this app from several sources — a model's streamed tokens, a saved transcript, a file's bytes — and those sources routinely carry mixed line endings: `\n`, Windows `\r\n`, and occasionally a lone `\r`. That text is then handed, unnormalised, to several **independent** renderers, and **each renderer owns its own line-splitting rules**: `prose()` splits on fences and paragraph gaps and `split('\n')`; `digest.js` scans for its block openers; `response-blocks.js` runs a per-line predicate. Each of those rules is written against the author's mental model of a line, which is `\n`.

So the default behaviour of a newly written renderer is to be blind to a `\r` it did not split on, and correctness is the exception that requires the author to remember a normalise step the code does not state and the type system does not enforce. It is not a mistake in the sense of writing something wrong; it is what you get by writing the obvious thing. There is no compiler error and no runtime error. Worse than "no visible symptom": the symptom is *invisible by construction* — a lone `\r` inside a collapsed fold hides an authored decision from the reader and from the accessibility tree (FEAT-091's `response-blocks.js` case, verified hidden in a real browser), or a `[^\n]*` strip runs past the break and deletes a whole line (BUG-109). The reader sees a shorter, plausible message and has no way to know a region is missing.

The second half of the design is that there is **no single point where "untrusted text becomes trusted-shape text" happens**. The boundary where content enters is not the boundary where it is normalised; normalisation is scattered to the leaves, one per renderer, and a new leaf starts life unnormalised.

## Why local patches did not hold

- **FEAT-091, `response-blocks.js`.** Fixed by stripping/normalising `\r` at that grammar's entry (a trailing `\r` on an info string was misclassifying a compliant reply; a lone-CR reserved opener hid an authored answer). Correct for that module. It said nothing about any other renderer, and did not prevent the next instance — which was found in a *sibling* module by a generated corpus only after this one was closed.
- **FEAT-091, `digest.js`.** Fixed by normalising `\r\n?` at `renderAssistantText` / `renderBody` / `parseDigest` — the transcript's front door. Correct, and it made assistant messages safe. But it protected only the callers that flow through the digest path; every other consumer of the shared `prose()` renderer still handed it raw text.
- **BUG-109, `dom.js` `prose()`.** Fixed by normalising all three endings as `prose()`'s first act (`/\r\n/g` → `/\r\n?/g`), inside the renderer so no caller can forget. Correct, and it closed eight exposed caller paths at once. But it is still one more renderer independently remembering to do the same thing, and it leaves the *next* renderer — one not yet written — exactly as exposed as `response-blocks.js` was before its own fix.

The pattern is the whole argument: **each fix was correct for its module and none of them prevented the next.** Three renderers, three separate remediations, same root, one day. The design is what is wrong, not the patches — patching a leaf cannot make a sibling leaf safe, because the omission is the default and every leaf must independently opt out of it.

## Decision — normalise once at the boundary, mechanically enforce per-renderer, or keep patching?

Priced against the observed rate: **three instances in a single day, two of them silent content loss/hiding, zero of the three found by their own author's first test** (FEAT-091's CRLF misclass was caught by a neighbouring suite; digest by a generated corpus; prose by an adjacent lane). There are at least three renderers with line-shaped rules today and no barrier to a fourth.

- **A — normalise once at each untrusted boundary.** Collapse `\r\n?` → `\n` at every point where content enters from a model, a transcript, or a file — the socket/stream ingestion, the transcript loader, the file reader — so that all text is already canonical by the time any renderer sees it; renderers then carry no line-ending logic at all. *How it works:* one normalise per entry point, and a rule that renderers may assume clean input. *Cost:* you must enumerate every untrusted entry point and prove none is missed — the same "is the list complete?" problem the recurrence already shows we are bad at; a missed boundary reintroduces the whole class silently. *Gives:* the strongest guarantee where it holds — a renderer *cannot* see a `\r` because none survives ingestion — and renderers get simpler. *Gives up / risk:* the guarantee is only as complete as the boundary inventory, and "text entered somewhere we did not list" is exactly the failure mode that is invisible; it also does not defend a renderer that is later handed a raw string from a new, un-normalised source.

- **B — keep per-renderer normalisation, add a mechanical check that enforces it.** Leave each renderer normalising at its own entry (as all three now do), but add a build/commit-time check: any module containing a line-shaped rule (a split/replace/regex on `\n`, `^`, `$`) must normalise `\r\n?` before that rule runs, or the check fails. *How it works:* a grep/AST-shaped guard over the renderer modules, with a named allowlist for any deliberate exception. *Cost:* a day, not a refactor; no product behaviour moves; the guard itself must be written carefully enough to see a laundered `\r` (a value passed through a local before the rule). *Gives:* the property becomes observable **at commit time** rather than at the third adversarial round or the next generated corpus — and it is complete over *modules with line rules* rather than over *the list of renderers someone remembered to fix*. *Gives up:* it is a guard, not an elimination — an author can still launder the value, and correctness depends on a check outside the language. It is also the natural first step of A: the guard's inventory is the audit A needs.

- **C — do nothing further, keep patching each renderer as the class recurs.** *Price, stated honestly rather than defaulted into:* at the observed rate this is a new silent-content-loss instance roughly whenever a new renderer with a line rule is added or a new source path is wired, each one costing an adversarial round or a generated corpus to find *because it is invisible to ordinary use*, indefinitely, with no convergence signal — the three so far were found by luck and neighbours, not by the authors. It also spends the expensive resource (independent clean-room verification) rediscovering a known class. Defensible only if the renderers are being consolidated to one anyway; otherwise it is the most expensive option, because the cost is paid in reader trust and lost content, not just developer time.

## Migration path

Each step landable and verifiable alone, and each useful even if the next never lands:

1. **Land B first, as a ratchet.** Add the mechanical check over the three renderer modules, allowlisting nothing (all three already normalise, so it passes today). Nothing changes behaviourally; the check now fails any *future* module that adds a line rule without normalising — the class stops growing at commit time. This is the cheapest step and the one that makes the property observable at all.
2. **Extend the check to enumerate untrusted entry points.** Have it also list every ingestion path (socket, transcript loader, file reader) and mark which normalise. This produces the boundary inventory that option A needs and that nobody currently has — the honest measure of how large A really is.
3. **If A is chosen, normalise at each boundary in step 2's inventory, one entry point per commit**, and only then remove the now-redundant per-renderer normalise from a renderer once every source feeding it is proven normalised. Each commit keeps the FEAT-091 and BUG-109 suites green; each is independently revertable. Renderers keep their own normalise until the boundary that feeds them is closed, so nothing is ever briefly exposed.
4. **Decide A-vs-B at the end of step 2, not now** — the inventory is the evidence. If entry points are few and fully enumerable, A is safe and worth the simplification; if they are many or open-ended (new source paths keep appearing), B is the durable answer and A is theatre.

Rollback at every step is a single revert; the ratchet in step 1 is the only thing that must not be reverted quietly.

## Proof bar — and the thing that is hard to prove

The redesign is right if:
- **Completeness over modules, not over a list.** The check fails on *any* line-shaped rule that runs before a normalise, including in a renderer that did not exist when the check was written. This is the property no per-renderer fix and no enumerated test has.
- **A synthetic new leak is caught.** Add a fresh renderer with a `split('\n')` and no normalise; the check must fail before it can land. A check that could only fail on the three known modules proves nothing.
- **Behavioural equivalence still holds** for every renderer: output on mixed-ending input equals output on the LF-normalised same input — driven over realistic-state fixtures (streamed tokens, a real transcript, file bytes with `\r\n` and lone `\r`) through the real render path, not a clean minimal string. For the fold renderers, drive the real collapse/expand click-path in a real headless browser and assert the authored content is present in the accessibility tree, since the FEAT-091 failure was specifically *hidden*, not deleted.

**The observability difficulty, stated plainly:** "no content was ever lost or hidden" is **not** directly observable — a region that renders nowhere leaves no trace to assert against, which is exactly why all three instances were found by luck rather than by their author. So the behavioural bar can only ever sample. What *is* observable, and is therefore the real proof bar, is the **mechanical property**: no line-shaped rule runs before a normalise, machine-checked over the whole set of renderer modules. That is why option B's check — or A's boundary inventory, which is the same check pointed at ingestion — is the bar, and the behavioural equivalence tests are corroboration, not proof.

**What would falsify the redesign:** if step 2's inventory shows untrusted text enters through a small, closed, fully-enumerable set of boundaries, then per-renderer normalisation (and its guard) is redundant overhead and A is strictly better — B would be maintaining a check for a property A makes structurally true. Equally falsifying: if the mechanical check produces frequent false positives on modules whose `\n` use is not a line-shaped *rendering* rule (e.g. a plain `join('\n')` for output), the guard is miscalibrated and will be disabled in practice — in which case the property is not mechanically checkable at the module granularity and the boundary approach (A) is the only real option.
