# ARCH-007 — laziness is implemented by interposition, so the station owns a protocol it does not implement

- **Status:** OPEN — NEEDS A HUMAN DECISION (4 options below). **No build starts until an option below is chosen.** Recommended: A — not because the defect rate proves the shape is unsafe (the sixth round HELD, and the curve may be flattening), but because A is the only option that deletes the station-owned protocol code instead of hardening it, and it is the only one that also unblocks the half of BUG-116 that is still eager and was declared structurally unfixable.
- **Severity:** medium. Not higher: single-user local tool, nothing deployed, no user has ever reported a lost reply from this component, and the current implementation now passes an independent pass. Not lower: this is a component in the request path of every browser tool call, it has consumed five fix rounds and five independent verification dispatches, and the half of the original bug it was built to fix is still open for `container` isolation.
- **Area:** the browser MCP attach seam — `src/server/sbmcp-lazy-shim.mjs` (station-owned relay, 648 lines), `src/server/browser.ts` (`mcpServerFor`, `available`, `lazyShimPath`, `toolsModulePath`), `scripts/verify-bug-116-lazy-browser.mjs` (1,291 lines, 56 checks), and the browser adapter's own `src/daemon.mjs` / `src/mcp-stdio.mjs` in a sibling checkout outside this repo.
- **Reported:** 2026-08-19 by the user, from the observed rate: *"about the each verification round finding a way, seems ineffective? … if same thing keeps causing problems too much, review if whole architecture is to change instead of the fix."* Raised against the project's own three-strikes rule; this ticket is the verification they asked for, not agreement with it.
- **Recurrence evidence:** BUG-116 rounds 1–6 — one original defect and **six distinct relay defects** across five landed fix commits (`df13918`, `4f8d488`, `703a436`, `4954b65`, `608064f`), found by **five independent clean-room dispatches, of which the first four returned BROKEN and the fifth HELD**. Adjacent: BUG-108 (ruled out as cause, with a measurement), BUG-114 (the leaked-verification-browser family, which is what the "20+ browsers" observation is actually about — see the census below), BUG-035 (the two-shape MCP attach seam this rides on).

## Violated invariant

**Changing *when* a capability starts must not make the station responsible for *how* that capability's protocol is spoken** — mechanically: for every isolation shape, the command a session is handed for the browser MCP server is the capability's own entry point, so the number of station-written processes that must correctly answer a JSON-RPC request is **zero**.

That is testable as one line: `mcpServerFor(project).args[0]` must be a file owned by the adapter, not by `src/server/`. Today it is `src/server/sbmcp-lazy-shim.mjs` for `direct` isolation, so the count is one, and **every one of the six defects below is a way for that one process to break JSON-RPC**. None of them is a way to break "do not start a browser until someone needs it". If all six break the same sentence and none breaks the feature's own sentence, this is a class and not six bugs.

A second, narrower invariant sits underneath and is the one BUG-116 was originally about: **asking a capability what it can do must not start it.** BUG-116's round-1 log wrote this down and said it was "worth an ARCH ticket only if a second one shows up". A second one has shown up, in the adapter, today, unfixed and unnoticed: `sbmcp status` is implemented as `tools/call browser_status`, `callTool()` opens with `const p = await page()`, and `page()` touches `browser` — so *reporting whether the browser is running* is on the same path that *starts* it. That instance is invisible right now only because the daemon launches Chrome before it serves at all, which is precisely what option A changes; it becomes a live bug the moment laziness moves upstream, and is priced into A's migration below.

## The design that produces this class

The station wanted one boolean changed — Chrome starts on first use rather than at session start. The knob for that boolean lives in the adapter's daemon (`main()` does `await claimSocket(); reapOwnOrphans(); await launch(); serve();` — the launch is unconditional and precedes serving, so any request at all, including `tools/list`, brings Chrome up). The adapter is a separate checkout, so the station could not reach the knob without touching code it does not own.

So it reached the same outcome from outside, by **interposing a process in the stream**: a station-owned stdio server that answers the no-side-effect half of MCP (`initialize`, `ping`, `tools/list`, `resources/list`, `prompts/list`) from the adapter's own static tool table, spawns the adapter's shim only on the first `tools/call`, and relays everything after that.

The consequence is the structural cause, and it is not subtle: **to change one boolean about timing, the station took on the whole correctness surface of a JSON-RPC stdio server it does not otherwise implement.** That surface is not small and it is not the kind of thing a fixture written by its author covers:

- **framing** — several messages per chunk, one message across chunks, no trailing newline, multi-megabyte payloads;
- **correlation** — which reply belongs to which request, ids of any JSON type, ids reused while in flight, replies matching nothing;
- **liveness** — every accepted request eventually answered, from two answer sources running at wildly different speeds (microseconds for a local `ping`, minutes for a real page load);
- **process lifetime** — client EOF, provider death, provider hang, stdout backpressure, stdout gone, uncaught exceptions, an emptying event loop, and every catchable terminating signal.

The assumption that keeps turning out false is stated in the round-1 design note and is worth quoting because it is the whole class in one sentence: *"that makes relaying a byte copy: no id rewriting, no request table, nothing to get out of step."* Relaying is never a byte copy. The moment a process answers some requests itself and forwards others, it owns a scheduler, a ledger and a shutdown protocol — and it owns them in a component whose entire product purpose is to do nothing.

## Why local patches did not hold

Every one of these fixes was correct for what it addressed. That is the point: the class kept being reachable somewhere else.

| round | commit | defect found by the clean room | what it patched | what it left reachable |
| --- | --- | --- | --- | --- |
| 1 | `df13918` | — (the original bug) | discovery served locally; nothing spawned until first use | the entire relay surface, unexamined |
| 2 | `4f8d488` | malformed client line logged and dropped, caller waits forever; replies overtaking each other | `-32700`; a FIFO outbox with in-order release | the FIFO itself — an ordering constraint the protocol never asked for |
| 3 | `703a436` | a hung provider silenced the whole channel (0 bytes on stdout for a `ping` answered in microseconds); stdin EOF killed the provider and exited 0, discarding accepted work | FIFO deleted; replies written when they exist; EOF drains | the ledger tracked only *forwarded* work |
| 4 | `4954b65` | a locally-answered `tools/list` followed by EOF: exit 0, zero bytes written | one ledger via a single `accept()` constructor; `owedBy`; a table of every reply-owing path × every exit path | the signal row of that table was hand-written |
| 5 | `608064f` | `SIGQUIT` took its default action and killed the process with the ledger unsettled | the terminating-signal set derived from `os.constants.signals` minus a reasoned exclusion list | (nothing found) |
| 6 | — | **HOLDS.** Excluded signals delivered to a live shim, signals with a local answer in flight, two in succession, a signal at startup: all survived | — | see the caveats below |

Two honest observations that cut in **opposite** directions, and both belong here.

**Cutting against the interposer.** Rounds 2–5 are four consecutive independent passes finding a real defect that a 40-, 50-, 56-check author suite had passed over, and the pattern within them is one shape repeated: *the fix was right about what it addressed and left one member of a hand-listed set unconsidered* (a set of parse outcomes; a set of exit paths; a set of answer sources; a set of signals). That is what owning a protocol surface feels like when you did not intend to own one — the sets are large, and the author does not know their boundaries because implementing them was never the goal.

**Cutting for the interposer, and this is the part the trigger question did not have.** Take the six defects and ask, one by one, whether the adapter's *own* shim — 193 lines, in the same position in the same stream, in production for months — has the same hole today:

| defect | adapter's own `mcp-stdio.mjs` today | verdict |
| --- | --- | --- |
| malformed line dropped, caller waits forever | line 181: `catch { err(...); continue; }` — identical | **inherited, not introduced** |
| replies out of request order | writes each reply as it exists; never had a FIFO | **self-inflicted by round 2, reverted in round 3** |
| a hung provider silences the channel | cannot happen — no FIFO | **artifact of the fix cycle only** |
| stdin EOF discards accepted work | line 188: `process.stdin.on('end', () => process.exit(0))` — identical | **inherited, not introduced** |
| a locally-answered request lost at EOF | same line 188, same hole, for `initialize`/`ping`/`tools/list` | **inherited, not introduced** |
| an unhandled terminating signal strands the reply | no signal handlers at all | **inherited, and worse there** |

So four of the six defects are **not caused by interposing**: they are the ordinary hazards of any hand-written stdio JSON-RPC server, they exist unfixed in the code that would be in the path if the interposer were deleted tomorrow, and nobody has ever hit them in real use. Two of the six existed only inside the fix cycle itself. The defect rate is therefore not measuring "interposition is dangerous"; it is largely measuring **what happens when an adversarial clean-room standard is applied to a hand-written protocol server for the first time** — a standard the adapter's own shim has never been held to.

That is the even-handed conclusion the trigger asked for, and it does *not* say the interposer is fine. It relocates the argument: the problem is not the extra hop, it is that **the station now hand-writes a protocol server at all**, and it did so to change a timing boolean. The way to make the class unreachable is to not have that file — which is option A — or to stop hand-writing it — which is option B. Continuing to harden it (option C) is defensible, and is now *more* defensible than it was yesterday, but it buys a hardened copy of a component whose ideal size is zero.

## Weighing the sixth round honestly

The sixth pass HELD. That materially weakens the "the rate proves the design" reading, and this ticket does not lean on that reading. Three things temper it, and one thing survives it:

- **Reduced decorrelation.** All five BROKEN verdicts were cross-provider. The HOLDS fell back to the author's own provider after four failed cross-provider handshakes. A same-provider HOLDS is weaker evidence than a cross-provider BROKEN; it is not zero evidence, but the two are not on the same scale.
- **Re-attack was partial.** The earlier rounds' properties (payload size, chunk framing, backpressure, correlation) were re-run through the *builder's own* suite in the clean room, not independently re-attacked.
- **Two gaps were named and left.** "Does not interfere with child process management" is proven only against a stub inner process, never against the real daemon reaping a real Chrome; and real-time signals (`SIGRTMIN`..`SIGRTMAX`) get no handler and would strand the ledger — declined as a defect because they are application-defined, which is a reasonable call and still an un-handled column.
- **What survives it:** convergence of the relay does not close BUG-116's other half. `container` isolation is still eager, still launches Chrome at session start, and BUG-116 argues at length that it cannot be fixed from the station side — the socket must exist before the bind mount, the socket only exists while the daemon serves, and the container is deliberately forbidden to spawn anything. Every option except A leaves that where it is.

## Decision — move the laziness into the capability, stop hand-writing the protocol, or keep hardening the relay?

Priced against what has actually been spent: **5 fix commits, 5 independent verification dispatches, ~3,100 net inserted lines across the shim and its suite, 648 lines of station-owned protocol code, and a 56-check suite of which roughly 40 checks exist solely to police that code** — against a feature whose entire content is "answer five methods from a static table and spawn on the sixth". And against what is still owed: `container` isolation, unfixed.

- **A — move the laziness into the capability and delete the interposer.** The adapter's daemon stops launching Chrome in `main()` and launches it, single-flight, on the first op that actually needs a page; the station points `direct` back at the adapter's own shim and deletes `sbmcp-lazy-shim.mjs` and the ~40 relay checks. *Cost:* changes a sibling checkout that is **not under version control today** (no `.git`, no remote) — so the real first cost is putting it under version control and giving the station a way to assert it is running a lazy-capable adapter, not the code change; the code change itself is not the "about five lines" BUG-116 estimated but roughly 10–20, because `sbmcp status`/`stop`/the orphan reaper read a `daemon.json` written inside `launch()`, and `browser_status` is a *tool*, so a naive patch would make asking the status start the browser — the very invariant this ticket names. *What it makes impossible, not merely unlikely:* every defect in station-owned relay code, by absence — there is no relay, no ledger, no signal set, no framing, no second answer source, and the invariant above becomes a one-line assertion instead of a 56-check suite. *What it buys beyond that:* `container` becomes fixable for the first time — the station can start the daemon (cheap, no Chrome) at session start so the socket exists for the bind mount, and Chrome comes up on the host at the first tool call from inside. *What it gives up:* the adapter's own pre-existing holes (malformed input, EOF, signals) return to being the accepted status quo rather than something we have proven; they are latent, never observed in real use, and can be fixed once in the file that already ships them. *New risk it introduces:* a launch race — N concurrent first calls must launch exactly one Chrome — which today's design cannot have because the launch is serialised by being first. That is one promise-shaped single-flight and is in the proof bar.

- **B — keep the interposer, but stop hand-writing the protocol.** Rebuild the shim on `@modelcontextprotocol/sdk` (the same SDK the clients use) or an off-the-shelf proxy, so framing and correlation are owned by a library with users, and the station's own code shrinks to the policy: "answer these five methods from the table, spawn on anything else". *Cost:* a rewrite of the component that has just reached a HOLDS, and a dependency in the host-side shim (acceptable — only the *container* shim must stay dependency-free); the SDK's per-request timeout defaults would need care for calls that legitimately run for minutes. *What it makes impossible:* the framing and correlation classes (defects 1, 2, 3 above) — a library that thousands of clients exercise does not lose a reply to a chunk boundary. *What it does not:* process lifetime and signals (defects 4, 5, 6) stay station-owned, because when to exit is policy, not transport. *What it gives up:* it keeps a station-owned process in the path forever, and it leaves `container` exactly as unfixed as today. Honest framing: this is the best option **if** the adapter must not be touched.

- **C — keep the current relay, change nothing, spend only on new evidence.** The relay is now derived-not-listed on both dimensions (answer sources by the single `accept()` constructor, signals by `os.constants.signals` minus a reasoned exclusion set), and the sixth pass found nothing. *Price, stated rather than defaulted into:* 648 lines of protocol code in the path of every browser tool call, maintained by whoever next edits it, with a 1,291-line suite that must keep passing; the two gaps the sixth pass named (real-time signals, child-process interaction against a real daemon rather than a stub) stay open; `container` stays eager, so the bug the user reported is still half-live; and the next independent round costs a full cross-provider dispatch to tell us whether the curve really flattened. *When it is right:* if the browser feature is about to be dropped or the adapter is about to be replaced, hardening what exists is strictly cheaper than any migration.

- **D — delete the requirement instead of implementing it.** Make the browser per-session opt-in (a session-start toggle) rather than a project-level setting, and let it start eagerly for the sessions that opt in. *Cost:* a UI/settings change and a behaviour change the user must accept — the model can no longer decide mid-task that it needs a browser in a session that did not ask for one. *What it makes impossible:* the interposer, entirely, and with it every defect above, at the price of the capability being less available than the model's tool list claims. *Why it is listed:* it is the only option that questions whether "always attached, lazily started" is the right product shape at all, and this project's own working style says to try the deletion test before building. Weak on its own merits — a tool the model cannot reach when it needs it is a worse failure than a warm daemon — but it is the honest floor of the price range.

## Migration path (for A; steps 1–2 are worth doing under any option)

1. **Put the adapter under version control and pin it.** It is a live dependency in the request path with no history, no remote and no way to say which version is installed. Nothing else in this list is safe until this is true. Landable alone; rollback is nothing (it changes no behaviour).
2. **Add a capability precondition to `available()`** — the station asserts the adapter reports lazy support (a `--lazy`/capability probe or a version field), and fails the session loudly if not, exactly as it already does for a missing `tools.mjs`. Landable alone; with today's eager adapter it simply reports "not lazy-capable" and the current shim keeps running. This is the step that makes step 3 revertable in one line.
3. **Adapter step: make the launch lazy.** `main()` drops `await launch()`; `daemon.json` is written at `serve()` time with `chromePid: null` and updated on launch, so `sbmcp status`/`stop`/`reap` keep working before Chrome exists; `callTool()` gains a single-flight `await ensureLaunched()` **except** for `browser_status`, which must report `running: false` without starting anything (the second instance of this ticket's narrower invariant — fix it here, in the same commit, or the migration re-creates the original bug in a new place). Verified in the adapter's own `test/` and by this repo's `verify:browser` against a patched checkout, before anything in the station changes.
4. **Station step: point `direct` back at the adapter's shim** (`mcpServerFor` drops `lazyShimPath()`, keeps `SBMCP_IDLE_MS`), behind the step-2 precondition. The station's behaviour is identical if the adapter is lazy and refuses the session loudly if it is not. One-line revert.
5. **Delete `sbmcp-lazy-shim.mjs` and reduce the suite** to the property tests that survive the redesign: no station-owned file in the MCP command line; `tools/list` starts zero Chrome processes (with a live must-FAIL control against the eager daemon); the first `tools/call` renders a real page; concurrent first calls launch exactly one Chrome. The ~40 relay checks and the three historical must-FAIL controls go with the file they test — they assert properties of deleted code.
6. **Container step, the payoff.** Start the daemon (not Chrome) at session start so the socket exists for the bind mount; the container shim keeps `SBMCP_AUTOSTART=0`; the first tool call from inside brings Chrome up on the host. `verify:container`'s isolation checks must stay green throughout — this step touches the security boundary and is the one that warrants its own independent pass.

What stays working throughout: every step leaves the browser tools functionally identical from the model's point of view, and steps 2 and 4 are the only ones that can change session-start behaviour. Rollback for the whole migration is reverting step 4; the shim file returns unchanged until step 5, which should not land until step 6 is proven.

## Proof bar — what would have to be true to call the new design right

- **The invariant, mechanically.** For every isolation shape, the command handed to a session names a file outside `src/server/`. This check cannot pass today and is the single assertion that replaces forty.
- **The feature, unchanged, with a live must-FAIL control.** A real CLI session against a browser-enabled `direct` project, one message, no tool use: **zero** Chrome processes counted from `/proc` for that project's `--user-data-dir`, and the same run must show the pre-lazy adapter starting ~10–13. A laziness test that cannot fail on the eager path proves nothing.
- **The new race the redesign introduces.** N concurrent first `tools/call`s (N ≥ 8) must produce exactly **one** Chrome root process and N successful replies. This is the failure mode option A creates and today's design cannot have; it is the first thing an independent pass should attack.
- **Asking must not start.** `sbmcp status` / the dashboard's browser card against a lazy daemon reports `running: false, chrome_procs_live: 0` and leaves the count at zero afterwards. This is the second instance of the narrower invariant and it must be proven, not argued.
- **Container, at the security boundary.** Socket present at session start with zero Chrome processes; the first in-container tool call renders a real page on the host; `verify:container`'s cross-project isolation checks unchanged and green. Independent verification required for this step specifically.
- **The relay defects, proven gone by absence.** Not re-tested — asserted unreachable by the first bullet. If any of the six can still be expressed after the migration, the migration is incomplete.

**What would falsify this.** If, after A, the *adapter's* shim starts producing lost replies in real use — not in adversarial fixtures — then the class was "any hand-written stdio JSON-RPC server", moving it upstream bought only silence, and B (an SDK-owned transport, applied inside the adapter) is the right answer instead. Equally falsifying, in the other direction: if step 1 reveals the adapter cannot be safely modified (shared with something else, or a dependency we do not control), then A's premise is wrong and the choice is genuinely between B and C. And if a seventh round never comes — if the relay stays quiet under two more cross-provider passes — then C was right on the rate, and A should be argued on the container half and the 648 lines alone, which is where this ticket already puts it.

## Evidence: the "twenty-plus browsers in an hour" observation, counted

The user observed a browser being spawned twenty-plus times during an hour of verification. Measured from `/proc` at the time of writing, root browser processes (excluding `--type=` children and crashpad helpers):

| what | count | evidence |
| --- | --- | --- |
| the user's own daily-driver browser | 1 | `ppid=1`, default profile, started 5 days ago |
| leaked headless verification browsers | 8 | all `--headless=new`, all with scratch `--user-data-dir` (`cs-f091r-chrome-*` ×3, `md-p-*`, `f091-prof-*`, `orch-r10-chrome-*`, `tbr-look/prof-*` ×2), **all reparented to `systemd --user`** — i.e. their spawners are gone |
| stealth-browser (BUG-116's browser) | **0** | no process with the adapter's Chrome-for-Testing path or a project `chrome-data` profile |

Three findings, and they answer the question in different directions:

1. **None of them is BUG-116's browser.** Zero. The browsers on this machine are the UI/renderer verification family — headless Brave driven over CDP by roughly twenty `verify-*.mjs` suites, each of which legitimately launches one or two per run. In an hour with several lanes running, twenty-plus launches is the expected number, not an anomaly.
2. **Process-count inflation explains most of the "twenty".** One browser instance is 5–13 OS processes (zygote, gpu, network, storage, renderers, crashpad). Counting processes rather than instances turns two or three browsers into twenty-plus. BUG-116's own repro measured "13 processes" for a single window.
3. **There is a real leak, and it is not this ticket's.** Eight orphans spread across two days, three of them started in the same second by one renderer suite, every one reparented to the user's `systemd` — their harnesses exited without closing them. That is the **BUG-114** family (verifier processes escaping their harness), and it is the thing actually worth fixing about the browser count. It is filed there; this ticket does not annex it.

**Is the suite heavier than the property requires?** For BUG-116, yes, and quantifiably: of `verify-bug-116-lazy-browser.mjs`'s 56 checks, about 16 concern the wiring and the laziness property, and about 40 concern the relay — framing, correlation, ledgers, exits, signals — driven against a **stub** provider that starts no browser at all. Only three checks start a real Chrome (the eager must-FAIL control, the first real `tools/call`, and the real-bridge session). So the suite is not what is spawning browsers, and it is not disproportionate to the *code it must police* — it is disproportionate to the *feature*, because roughly two thirds of it exists to prove that station-owned protocol code is correct. Under option A that two thirds is deleted along with the code it tests, which is the clearest single price signal in this ticket.
