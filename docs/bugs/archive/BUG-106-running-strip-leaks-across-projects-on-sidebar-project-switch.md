- **Status:** FIXED (Option A + clean-room defects A & B remediated) — an INDEPENDENT re-verification of the remediation is owed before VERIFIED.
- **Verified-by:** self (verify-bug-106-crossproject-strip.mjs 33/33 + verify-msg-timestamp-hover.mjs 24/24 + must-FAIL for both clean-room defects); the openai/codex clean-room pass (below) returned BROKEN on the prior state and its two findings are now fixed — a fresh clean-room pass over the remediation is still owed (scoping/observability-honesty fix — see Verification-class). HIGH-STAKES (observability + a11y, regression-prone family): an independent clean-room re-verify is warranted.
- **Severity:** medium — no data is lost or corrupted, but an observability surface lies: it attributes one project's live work to a different project, which is exactly the class of "the fleet view tells you the wrong thing" this app treats as serious.
- **Area:** client — `public/app.js` (`selectProject` / the running strip + permission hairline in the transcript dock). NOT the server: the running set is correctly scoped per session.
- **Reported:** 2026-08-18, by the user, watching the dashboard while an agent ran in the orchard project.
- **Verification-class:** fix ⟶ independent verification REQUIRED before VERIFIED (it is a scoping/observability-honesty fix, the regression-prone family that BUG-083 already sits in).

## Symptom

The user was looking at a DIFFERENT project and still saw, verbatim:

> "Running / 5:37 / worker / Test cheap-model claim checking / 5:37 / Permissions skipped · container is the boundary" appears btw even when im on another project, basically unrelated projects get same list

That row is a real agent that was dispatched in the **orchard** project. It stayed on screen — clock ticking — while the user had navigated to an unrelated project. Every project "gets the same list": the Running strip does not change when you switch projects in the sidebar.

## Why this is NOT a server leak (the reported guess was: state is served globally)

The running set is authored on the SERVER, per session, and is correct. `snapshotOfSession` (`src/server/running-set.ts`) builds one snapshot for one `AgentSession`; the push event (`running-snapshot`) is sent only on that session's own driving socket; the poll route `GET /api/sessions/:id/running` answers for one session id. Nothing broadcasts one project's activity to a client that asked about another. The client is asking for the RIGHT session — the problem is that it keeps asking for, and drawing, the session it had OPEN, even after the user selected a different project in the sidebar.

So this is a client view-coherence bug, not a data-scoping bug on the wire. Filtering-at-the-source is not applicable here because the source is already scoped; the incoherence is created entirely inside the client when the "project in view" is changed without changing (or re-scoping) the transcript dock that the strip lives in.

## Is there a legitimate "everything running everywhere" view this would destroy?

No such global view exists today — checked. The strip is a single element in the transcript dock (`#strip` / `#stripRows` in `public/index.html`), bound to the one open session. There is no per-project running badge in the sidebar and no global activity feed. So there is nothing intentional to preserve here; the strip is meant to describe the session you are looking at, and today it describes the session you last OPENED, which after a bare project-switch is a different thing.

## Repro (reproduced — real evidence below)

1. Open a session in project O (e.g. orchard) that has a live subagent → the Running strip shows it (`worker · <description> · 5:37`), and if O is a container project the permission hairline shows "Permissions skipped · container is the boundary".
2. In the sidebar, click a DIFFERENT project's header (project P) — WITHOUT opening any of P's sessions. This is the ordinary "look at another project" action.
3. Bug: the strip (and the permission hairline) still show project O's running agent, under project P. The clock keeps ticking. The 4s poll keeps refreshing O's running set forever.

## Expected

When the selected project is not the one that owns the open session, the Running strip and the permission hairline must not present that session's live work as if it belonged to the newly-selected project. Concretely: switching projects in the sidebar must re-scope the strip the same way opening a session does — it must not leave a foreign project's running rows on screen. A fix that simply hides everything is worse than the bug: the per-project view must still show that project's OWN running work, an empty project must show nothing, and switching back must restore the real state.

## Technical detail (reference — skip unless you are fixing this)

### Root cause

`selectProject(id)` (`public/app.js` ~line 3984) is the sidebar "look at this project" action. It mutates `state.current.projectId = id`, repaints the crown and the right rail (board/outcomes), and returns. It does **not** touch the transcript dock: `state.snap`, the strip DOM, the permission hairline, the driving socket, or the running-set poll. All of those remain bound to whatever session is OPEN.

The only thing that clears `state.snap` and re-scopes the strip is `resetTranscript()` (`public/app.js` ~line 2580: `state.snap = null; state.snapScope++`), and it is called **only** from `openSession()`. So opening a session in project P clears the strip; merely *selecting* project P in the sidebar (the `head.addEventListener('click', …)` at ~line 883, which calls `selectProject(p.id, { quiet: true })`) does not.

The poll makes it persist rather than merely lag: `pollRunning()` (~line 5272) fetches `state.stationSessionId || state.sdkSessionId || state.current.sessionId` — the still-open session — every `SNAP_POLL_MS` (4s), so O's running set is actively re-fetched and re-applied while the user is on P. `snapshotIsForCurrent()` accepts it because the ids still match the open session.

After `selectProject(P)`, `state.current` is internally inconsistent: `projectId` is P, but `sessionId`/`encodedDir` still point at O's session. The strip and the permission hairline read the open session; the sidebar/rail/crown read the selected project. They diverge.

### Recommended fix (the WHERE decision — needs the orchestrator's UX call before building)

The scoping belongs in the client, at the `selectProject` boundary — the server is already correct, so there is nothing to scope at the source. The open question is the intended behaviour, and it is a UX decision, which is why this is filed OPEN rather than fixed in this lane (the charter's explicit "if the data is correctly scoped and the client is showing a stale/foreign view → STOP and report" case):

- **Option A (minimal, recommended):** gate the strip + permission hairline on "the open session belongs to the selected project". Track the open session's owning project separately from the sidebar-selected project (today `selectProject` overwrites the single `state.current.projectId`, destroying the distinction), and when they differ, render the strip/hairline as empty/absent — the same end state `resetTranscript` produces — WITHOUT closing the open session or clearing its transcript. Must also stop or ignore the running-set poll while the open session is foreign to the selected project.
- **Option B:** treat a project-header click that lands on a project with no open session as a full navigation (like `openSession` for a "no session yet" state), so the whole dock re-scopes. Heavier; risks throwing away the open conversation the user may want to return to.

Whichever is chosen, the four cases the verification must cover: (1) the leak direction — foreign strip must clear on project switch; (2) the OWN direction — a project's own running work still shows when it is selected; (3) an empty project shows nothing; (4) switching back to the project that owns the running session restores the real strip. Extend `scripts/verify-bug-083-project-switch-state.mjs` with the `selectProject` boundary (or add `verify-bug-106-*`), and this being an observability/scoping fix, add a `Verified-by:` clean-room dispatch line before VERIFIED.
