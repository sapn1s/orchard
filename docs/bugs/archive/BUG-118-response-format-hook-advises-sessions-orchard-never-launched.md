# BUG-118 — the response-format Stop hook advises sessions Orchard never launched

- **Status:** IN-PROGRESS — round-4 fix landed (DELIVERY: the hook is re-synced by ordinary onboarding and repaired at every launch, or the failure is announced); awaiting a fourth independent verification
- **Severity:** high — it puts this project's rules into a stranger's turn. Not data loss, but it is the worst kind of noise: unsolicited, wrong, and in the middle of someone's real work, in a project that has nothing to do with Orchard. It also lands in every project onboarded so far, and each one is a place the user may never think to look.
- **Area:** onboarding / response-format Stop hook / session launch provenance
- **Reported:** 2026-08-19, by the user, from a hand-started `claude` session in an unrelated project
- **Verification-class:** fix ⟶ independent verification REQUIRED before VERIFIED. The change is a silencing gate on a hook that runs in every onboarded repo, so the two failure directions are opposite and both matter: too loud (advises strangers again) and too quiet (never advises anyone, and nobody notices for weeks).

## The argument

The user started a plain `claude` in a different project, working on unrelated product code, and got this:

> Stop says: Response-format advisory (not enforced): Your reply does not meet this project's response guidelines. Missing the leading orchard-digest block…

That session was not launched by Orchard. It has nothing to do with this app's reply format. The advisory was pure noise, and it landed mid-task.

**The mechanism is the feature working as built.** Onboarding installs the hook into the target project's OWN `.claude/settings.json`, which is exactly what makes the method travel to every onboarded repo. But Claude Code runs a project's Stop hooks for **any** session whose working directory is that project — including a bare `claude` the user starts by hand. The hook had no way to tell those apart, so it graded both.

**Nothing in the Stop payload says who launched the session.** That was checked against a real payload captured live, not assumed: session id, transcript path, cwd, prompt id, permission mode, effort, event name, `stop_hook_active`, last assistant message, background tasks, crons. A hand-started session and an Orchard-launched one are identical on that wire.

So the hook has to be **told**, and the one channel that reaches it is the environment its CLI was spawned with — hook commands are children of the CLI, which was confirmed live. Orchard stamps `ORCHARD_SESSION` on that spawn environment, and the hook is inert without it.

**But a flag is not enough, because a flag is inherited.** Round 1 stamped `ORCHARD_SESSION=1`, and an independent verification broke it in one move: a `claude` the user starts by hand in a terminal opened *inside* an Orchard session inherits that variable like any other, so it satisfied the gate and got advised — the original complaint, intact. The marker therefore carries the **session id** Orchard declared for that CLI, and the hook speaks only when it equals the `session_id` in its own Stop payload. A child inherits the value but never the identity: it gets its own new session id, so it can never match. See the round-2 log entry for the live measurements.

**It fails closed toward silence.** No marker means no advisory, no matter what else is set — including a globally enabled enforce mode, which can no longer block a stranger's turn. A false advisory in someone else's work is worse than a missed one in ours, because this format only matters for replies Orchard itself renders.

**A fix that cannot reach the copies is not a fix.** Onboarding never clobbers, by design, so every project onboarded before today would have kept the noisy hook forever. The hook file is the one installed artifact no other repo could plausibly own, so it is now the one thing `--force-hook` re-syncs — and the fleet sweep carries it. Nothing else the target owns is touched.

**What this deliberately does not cover:** a session Orchard merely *follows* and renders but did not spawn. We cannot put an environment variable into a process we did not start, and such a session was never given the response-format instruction in the first place, so grading it would be advice about a rule it never received. Silence is the honest answer there.

**Neighbouring artifacts, checked:** the Stop hook is the only thing onboarding installs that fires by itself. The gate wrapper, the leak/NUL guards and the board tooling are all invocation-only npm scripts — they run when someone runs them. The one other thing that reaches a hand-started session is the `CLAUDE.md` pointer onboarding writes, which is Claude Code's ordinary project-instructions mechanism, is the point of onboarding a project, and was not part of the complaint. Left alone.

## Reproduction (real, not inferred)

1. Scaffold an empty project outside this repo and run `node scripts/onboard.mjs <dir>`. It writes `.claude/settings.json` with the Stop hook plus the hook's dependency closure.
2. Run a plain `claude -p "<any prompt>"` in that directory — no Orchard, no server, no dashboard.
3. The project's Stop hooks fire. Confirmed by a probe hook installed alongside the real one, which recorded the payload and environment of every turn.
4. Feed that captured payload to the hook and it emits the advisory verbatim:

```
[orchard stop-hook advisory] Your reply does not meet this project's response guidelines.
Missing the leading ```orchard-digest block. …
```

Two notes on fidelity, both worth keeping:

- **The live headless runs went quiet on their own**, and that is not the hook behaving. It is the FEAT-085 read-during-write race: in `claude -p` the final assistant line is not yet flushed when Stop fires, so the hook grades nothing and fails open. Replaying the *same* real transcript a second later produces the advisory every time. The user's evidence is an interactive session, where the flush has happened.
- Because of that, the sharp before/after evidence is the **real captured payloads**, replayed through the hook file that ships. Same file, same input, provenance the only variable.

## The fix

| Where | What |
| --- | --- |
| `scripts/hooks/response-format-gate.mjs` | Launcher gate (round 2): no `ORCHARD_SESSION` → `allow()` before anything is even read; and unless it NAMES this payload's `session_id` (directly, or via a launcher-recorded rename claim) → `allow()`, silently, ahead of every grading step. |
| `src/server/runtime/claude-runtime.ts` | Declares the session id (`Options.sessionId` → the CLI's `--session-id=<uuid>` for a fresh launch and for a fork; the resumed id otherwise) and puts it on the spawn env: `env: { ...process.env, ORCHARD_SESSION: declaredSessionId }`. The spread is load-bearing: the SDK's `env` **replaces** the child environment rather than merging, so dropping it would strip the boot-augmented PATH that BUG-091 exists to deliver. Also watches its own stream for an id that drifts from the declaration and claims it (`claimLaunchedSession`). |
| `src/server/container-manager.ts` | `ORCHARD_SESSION` added to `ENV_PASSTHROUGH`, so it crosses the `docker exec` boundary — a containerised session runs the hook *inside* the container against the mounted repo's settings. |
| `scripts/onboard.mjs` | `--force-hook` re-syncs `scripts/hooks/response-format-gate.mjs` over an existing copy. Scoped to that one file: the rest of the method closure has names a target repo can plausibly own (`scripts/gate.mjs`, `public/lib/dom.js`), and overwriting those would destroy the target's own code. |
| `scripts/fleet-sync.mjs` | The hook joins `SYNCED_TOOLS`, so the fleet sweep keeps it current — the same gap that let `verdict-contract.mjs` rot in every copy. |

### Why the environment, and not the alternatives

- **The payload** carries no provenance (checked against a live capture) — but it does carry the session's IDENTITY, which is what round 2 keys the environment marker against.
- **The registry / session store** is reachable only on the host; a containerised session's hook runs inside the container with no view of it. That is why the identity is carried on the env (which crosses `docker exec`) rather than looked up. Fork and resume renaming is handled by declaring the id in the first place: a fork is told its new id, a resume keeps the one it resumed (both measured live).
- **A marker file in the project** would be per-project state, which is exactly the opt-in-per-project shape the fix was told not to take, and it cannot distinguish two sessions in the same directory.

### The three ways an Orchard session starts, each checked

- **Fresh launch** — the marker is on the SDK spawn env; the real fake-CLI child records it.
- **Resume / open** — a resume is a new spawn down the same path, so it is the same code and the same marker.
- **Survivor after a service restart** — the surviving CLI is the *same process*, still holding the environment it was spawned with, so its drain turn's hook still sees the marker; the broker's scope env spreads the SDK env rather than curating it. The continuation after the drain is an ordinary resume spawn.
- **Container** — forwarded explicitly through `docker exec --env`.

No validation *inside* the hook can make that file trustworthy; only its absence can. It was covering a drift that has **never been observed in any live run**, and the cost of not having it is that the hook goes quiet for such a session — the direction this gate already declares is the correct bias.
- **Failure classes, precisely:**

Round 1's escape and round 2's escape are both closed by construction rather than by validation.
