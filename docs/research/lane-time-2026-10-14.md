# Where does the time go inside a lane? (fix vs check)

**Date:** 2026-10-14 · **Lane:** finding/explore (round 1) · **Dispatch:** `phase=finding round=1 class=explore`
**Question (user, verbatim):** *"which step takes most time, fix or check? where the time goes, i assume
maybe recompiling fresh dashboard? cant even pre-warm things or something to speed process? since usually
every change now take hours idk if solveable"*

Research only. No product code changed, no service touched, no git write. Scratch server boots used free
ephemeral ports and scratch data dirs (5 boots, all stopped by pid).
Prior data: `docs/research/ship-before-verify-2026-10-13.md` measured the split *by ticket phase*. This doc
measures what happens *inside* a lane.

## 0. Answer first (after refutation; see §5)

- **Fix vs check: checking takes most of the time.**
  - Counted by lane type, the two look even: fix lanes 53%, check 47%. This excludes quota blocks and counts nested verifier lanes once.
  - That count is misleading. Fix lanes spend 1,060 min running suites, browser runs and the gate, which is checking.
  - Counted by activity instead: **writing the change takes about 37%, checking about 63%.**
  - The refuter estimates **about 27/73** if the test and probe code written inside fix lanes also counts as checking.
- **Your guess (recompiling the dashboard) is wrong for the dashboard.**
  - Orchard has no dashboard build: no bundler, no compile. The server runs `.ts` directly.
  - A scratch server boots in **0.5 s** (measured 5×). Inside the suites, boot overhead is 1–4% of suite time (refuter timed 3 suites).
  - A pre-warmed server would save **under 1 min per ticket**.
- **What the method missed: Docker.** Suites that run Docker containers took **478 min, 41% of suite machine time** (refuter).
  - Many new container images were built: 26 or more `claude-station-rt` runtime images on 10-13, and 6 `orchard-confined-run` images overnight on 10-13/14 (`docker images`).
  - How much of the Docker time is image builds is **not measured**. Some of it is product timers, such as a 240 s rebuild wait.
  - This is the one place where pre-warming or caching could matter.
- **Where lane time goes (all 311 lanes):**
  1. **Model thinking/generation: about 31–35%.** This is the largest share.
  2. **Waiting on a child verifier: 21%.** The OpenAI clean-room run itself is about 85% model reasoning and 15% tool execution.
  3. **Waiting for quota: about 13%** for the limit window itself, plus about 12% waiting for someone to resume the lane after the reset.
  4. **Suites, browser runs and gate: about 12% overall, and 23% inside fix lanes.**
  5. **Untangling a candidate tree: about 0.5%.**
- **Why a ticket "takes hours":**
  - BUG-255 took 15.7 h on the clock. No lane was running for 7.9 h of it (overnight, waiting for the orchestrator or the user). 3 h was a quota block. Lane work was about 4.8 h over 4 rounds.
  - The other three tickets (FEAT-181, BUG-256/257, FEAT-184) took 1.0–1.2 h each.

## 1. Method and N

- **Lanes, N = 311** (out of 313 analyzed transcripts that had at least 3 tool calls):
  - **This orchestrator session (`20ed61fc`): 37 lanes.** This excludes my own lane and 2 empty lanes. It includes every BUG-255, FEAT-181,
    BUG-256/257 and FEAT-184 fix and verify lane, including the nested clean-room children.
  - **Contrast: 274 lanes**, from every other orchard session since 2026-10-08 (transcripts over 50 KB).
- **Classification:** each lane is classed **fix**, **verify** or **other**.
  - The main signal is the `Dispatch: … phase= class=` header.
  - The fallback is the lane's description.
  - Result: fix 89, verify 107, other 115.
- **Bucketing.** Each lane's timestamped records are sorted, and each interval between consecutive records is assigned to a bucket:
  - **One or more foreground tool calls outstanding:** the interval is split among those calls' categories.
  - **No tool call outstanding:** the interval is model time.
  - **The next record is a task notification:** the time is waiting on that background job.
  - **The next record is a coordinator resume after a "hit your session limit" message:** the time is a quota block.
  - **Any other coordinator resume:** the lane was parked between rounds. This is excluded from the shares: it is time spent waiting for the
    verify lane and the orchestrator, not lane work.
- **Waits on background jobs** (`tail --pid`, `kill -0` loops, `sleep`, Monitor) are attributed to the job they wait on. The job is matched by
  PID from the launch output, then by keyword, then by the most recent launch.
- **Command categories** come from regexes on the Bash text. The rules are in `analyze.py`.
- **OpenAI verifier internals:** 222 Codex rollouts since 10-08, read from their per-call `Wall time`. This is the time spent inside the codex child.
- **Direct measurements on this machine:**
  - Scratch-server boot, 5 runs through `scripts/lib/bug-187-harness.mjs`.
  - `npm run gate`: 8.0 s, of which leak-gate is 7.2 s.
  - `tsc --noEmit`: 0.5 s.
  - Clean-room setup: `node_modules` reflink copy in 0.93–1.01 s (from the real IV logs in `/tmp/*-iv.out`).
- **Scripts and data** are in `~/.local/state/claude-station/scratch/lane-time-2026-10-14/`: `analyze.py`, `report.py`,
  `boot.mjs`, `main.json`, `other.json`. Re-run with `python3 analyze.py $(cat main.txt) > main.json; python3 report.py`.
- **Limits:**
  - Bucketing uses regex classes. A Bash loop that runs several suites is counted under its first match.
  - When parallel tool calls overlap, the interval is split evenly among them.
  - Model time includes the time to stream tool *inputs*, such as a long Write.
  - Background suite runs are visible only through the waits on them. A lane that did other work while a suite ran
    shows that time as model time, which is the correct reading of the lane's critical path.

## 3. The user's guess: is build or dashboard compile a material share?

**No.**
- There is no `build` script and no bundler in `package.json`. The server is `node src/server/index.ts`.
- **Boot to `/api/health`: 0.5 s.**
- Across 311 lanes:
  - Boot/build: 149 min (1.4%). Of that, 124 min is in "other" lanes (backup/bench research), and 22 min is in fix lanes.
  - Gate: 108 min (1.0%). One gate run takes 8 s.
- What *is* material machine time is **running test suites inside fix lanes: 18% of fix-lane time** (851 min).
  The long ones are behavioural suites that boot several servers and drive real or fake CLIs, not builds. Examples:
  - `verify-bug-247-boot-starvation`: 48 min over 50 runs.
  - `verify-bug-244-container-git-readonly`: 78 min over 47 runs.
  - `verify-feat-170-shadow`: 28 min over 45 runs.
- In BUG-255 the browser suites (`verify-bug-255-*-ui`) cost 68 min in fix lanes.
- Foreground suite calls: median 0–1 s, p90 about 50 s. Most calls are quick. A few multi-minute suites run many times.

## 4. Levers, ranked by minutes saved per ticket

Baseline (this session, 4 tickets): per ticket, about 122 active lane-min plus 90 quota-blocked lane-min. Calendar
time is 1–1.2 h for clean tickets and 15.7 h for the hot one.

(Ranking and estimates below were put to an independent refutation. §5 has its verdict, and the
surviving list is the one to quote.)

| # | lever | evidence | est. saved per ticket |
|---|---|---|---|
| L1 | **Fewer rounds** (property-first verification, FEAT-180 corpus runner, FEAT-181 escalation) | rounds 2+ = 70% of ticketed lane-min here; a round costs ~60–120 lane-min and ~45–90 calendar min | 60–90 lane-min on multi-round tickets (≈ 30–45 averaged); unproven: FEAT-180 is an experiment |
| L2 | **Quota continuity** (account failover on a session limit, FEAT-160/FEAT-120; auto-resume at reset) | 9 limit hits; one block cost BUG-255 ~3 h calendar; 25% of all lane-minutes are quota blocks; reset→resume delay was 3 min here but 85–735 min in 4 of 6 earlier hits | calendar: ~180 min on a ticket that hits it (≈45/ticket here); auto-resume alone saves 0–735 min only where resume lagged |
| L3 | **Commit or freeze each ticket on landing** (FEAT-170 `candidate freeze`/`commit`), so verifiers don't rebuild a ticket-only tree | BUG-255 spent ~97 lane-min in 3 dedicated untangle lanes + small phases; clean tickets 0–5 min; 2.8% of all lane time | ~25–30 on hot-file tickets per round; ~0–5 otherwise |
| L4 | **Run independent suites in parallel / a per-round subset** (only suites touching changed files + the ticket's own; full sweep once at the end) | tests+browser = 21% of fix-lane time; BUG-255 93 min over 4 rounds | ~10–20 per multi-round ticket |
| L5 | **Flatten nested verifier wrappers** (orchestrator → verify lane → Opus child → IV/Codex) | BUG-255 r3: 3 levels (60 → 54 → Codex); each wrapper adds 5–15 own model minutes | ~10–15 per round where nesting occurs |
| L6 | **Close the no-lane gap** (auto-dispatch the next round when a verdict lands, instead of waiting for the orchestrator or the user) | BUG-255: 7.9 h of 15.7 h had no lane running | calendar only, large but presence-dependent |
| — | Pre-warmed scratch server / build cache | boot 0.5 s, no build; 1.4% total and mostly curl | **< 1 min — not worth building** |

### FEAT-170 shadow lanes default-on? (queued question)

The shadow-repo pilot was **removed by user decision on 2026-10-13** (CONVENTIONS §FEAT-170). The data here does
not reopen it:
- Untangling is **2.8%** of lane time overall.
- Of the 4 tickets in this session, 3 needed 0–5 untangle minutes. BUG-255 needed about 100.
- The thing that removes the untangle cost is **ticket isolation at verification time**. The candidate tools that were kept
  already provide it (`candidate freeze` → `independent-verify --candidate`), with no per-lane private repo.

Verdict: shadow default-on is **not** supported. Freeze each ticket as a candidate as a matter of course, which is L3.
